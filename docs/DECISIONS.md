Each entry: date, context, options considered, choice, reason. Newest at the bottom. To reverse a decision, add a new entry that references the old one. Never edit history.

## D-001 (2026-11-18): Development environment
**Context:** The host is macOS 15 on an Apple M3 Pro (arm64). The project needs epoll (Phase 6), perf (Phase 4) and Linux-specific socket options, none of which exist on macOS.
**Options:**
1. Build natively on macOS and swap epoll for kqueue. Rejected: trading firms run Linux, and two code paths would double the gateway work.
2. Docker dev container, linux/arm64 (native architecture, runs in Docker Desktop's VM).
3. Docker container, linux/amd64 under emulation. Rejected: emulated x86 makes every benchmark meaningless.
4. A remote Linux box (e.g. UIUC EWS, a cloud VM). Kept as an *additional* benchmark machine later, not the daily environment.

**Choice:** Option 2, an Ubuntu linux/arm64 container with GCC and Clang, entered via `scripts/dev.sh` or VS Code Dev Containers.
**Reason:** Real Linux APIs at native speed with no extra hardware needed.
**Consequences to remember:**
- `rdtsc` is x86-only. On arm64 the equivalent is the generic timer `cntvct_el0` (fixed frequency, lower resolution than TSC). The Phase 4 latency recorder must choose deliberately; that choice will get its own entry.
- Docker Desktop runs Linux in a VM, so benchmarks carry VM noise and every BENCHMARKS.md row must say so.
- perf inside Docker Desktop's VM may not have access to hardware PMU counters. **Not yet verified**; check in Phase 4 before relying on it. Software-event sampling (`-e cpu-clock`) is the fallback.

## D-002 (2026-11-18): Project documentation structure
**Context:** The project spans many work sessions, and anyone (including future me) should be able to resume it cold.
**Choice:** docs/PROGRESS.md (current state and next step), docs/DECISIONS.md (why), docs/ROADMAP.md (what), docs/BENCHMARKS.md (append-only numbers), docs/learn/ (study guides per phase).
**Reason:** Separating state, rationale, plan and measurements keeps each file short and easy to keep accurate.

## D-003 (2026-11-18): Phase 4 pre-split
**Context:** Phase 4 bundles a latency recorder, benchmark workloads, an ITCH parser with replay, and a profiling pass. That is too much for one session.
**Choice:** Planned sub-parts 4a (recorder + benchmarks), 4b (ITCH), 4c (perf hotspot fix). Other phases get split only when a split proves necessary.

## D-004 (2026-11-18): Project name
**Context:** The project needed a name for the repo, the C++ namespace and the binaries.
**Options:** ringmatch (from the ring buffers used between threads), litbook.
**Choice:** litbook. Namespace `litbook`, headers under `include/litbook/`.
**Reason:** A "lit" market is one with a publicly visible order book, as opposed to a dark pool where resting orders are hidden. That is exactly what this project builds: a lit venue that publishes its book over a market data feed.

## D-005 (2026-11-18): Build configurations via CMake presets
**Context:** Four build types are needed (debug, release, ASan+UBSan, TSan) on two compilers.
**Options:** (1) Document long `cmake -D...` command lines. (2) Shell scripts per configuration. (3) `CMakePresets.json`.
**Choice:** Presets: `debug`, `release`, `asan`, `tsan` (GCC) plus `-clang` variants, each building into `build/<preset>/` with Ninja.
**Reason:** Presets are standard CMake, understood by IDEs and CI, and keep every configuration reproducible from one name. ASan and TSan are separate presets because they cannot share a binary (both replace the memory allocator and shadow memory layout).
Sanitizer flags are applied globally (including GoogleTest), because TSan misses races and reports false positives when only part of the program is instrumented.

## D-006 (2026-11-18): Dependencies via FetchContent, pinned by hash
**Options:** (1) System packages. (2) vcpkg or Conan. (3) Git submodules. (4) CMake FetchContent.
**Choice:** FetchContent from release tarballs with SHA-256: GoogleTest v1.17.0, Google Benchmark v1.9.1, declared `SYSTEM` so their headers do not trigger project warnings.
**Reason:** No extra tool to install or explain; exact versions are pinned; the hash rejects a tampered or changed download. A package manager pays off only with many dependencies. Submodules add a manual `git submodule update` step that is easy to forget.

## D-007 (2026-11-18): Stricter warnings than the minimum
**Choice:** Beyond `-Wall -Wextra -Wpedantic -Werror`, also `-Wshadow -Wconversion -Wsign-conversion -Wnon-virtual-dtor -Wold-style-cast -Woverloaded-virtual`, applied per target through an interface library (`litbook::warnings`) so third-party code is unaffected.
**Reason:** Quantities are unsigned. A silent signed/unsigned or 64-to-32-bit conversion in matching code is exactly the bug class `-Wsign-conversion`/`-Wconversion` catch at compile time.

## D-008 (2026-11-18): CI runs on the native GitHub runner, not the dev container
**Options:** (1) Build the dev container image in CI and run inside it. (2) Use `ubuntu-24.04` runners with their preinstalled GCC 14 and Clang 18.
**Choice:** Option 2, a matrix of {debug, release, asan, tsan} by {gcc-14, clang-18}.
**Reason:** Much faster (no image build) and simpler. It also adds coverage: CI is x86-64 while development is arm64, so architecture-specific assumptions get caught. TSan on these runners needs `vm.mmap_rnd_bits=28` (a known ASLR incompatibility).

## D-009 (2026-11-18): One test executable
**Choice:** A single `litbook_tests` binary with all test files, registered through `gtest_discover_tests(... DISCOVERY_MODE PRE_TEST)`.
**Reason:** It links fast and every test is still visible to ctest individually. Discovery at test time (not build time) avoids running sanitizer-instrumented binaries during the build. Split into several binaries later only if link times grow.

## D-010 (2026-11-18): Dev image is Ubuntu 26.04 LTS with distro-default compilers
**Options:** (1) Ubuntu 24.04 (GCC 13/14, Clang 18). (2) Ubuntu 26.04 LTS (GCC 15.2, Clang 21). (3) Install newer compilers from the upstream LLVM apt repository.
**Choice:** Ubuntu 26.04 LTS with unversioned packages (`g++`, `clang`), installed versions GCC 15.2 and Clang 21.1.8.
**Reason:** Newest C++20/23 support from the standard archive with no extra package sources. Being newer than CI (GCC 14 and Clang 18 on ubuntu-24.04) is useful, because code must compile on both old and new compilers.
Verified 2026-11-18: ASan (heap-buffer-overflow), UBSan (signed overflow) and TSan (data race) all detect deliberate bugs inside the Docker Desktop VM with both compilers, and TSan needed no ASLR workaround there.

## D-011 (2026-11-18): `#pragma once` over include guards
**Choice:** `#pragma once`; clang-tidy's `portability-avoid-pragma-once` is disabled.
**Reason:** It is supported by every compiler targeted (GCC, Clang) and cannot go wrong by copy-pasting a guard name. Include guards are only needed for exotic compilers or headers reachable through multiple filesystem paths, neither of which applies here.

## D-012 (2026-11-18): Planning notes stay out of the repository
**Context:** D-002 set up docs for state, plan, rationale and measurements.
**Choice:** The roadmap, progress notes and study notes are kept locally and gitignored. Only this decisions log and the benchmark log are published.
**Reason:** The repository should present the engineering record (why things were built this way, and measured results), not personal to-do lists.

## D-013 (2026-11-18): Core numeric types
**Choice:** `Price = int64_t` (ticks), `Qty = uint32_t`, `AggregateQty = uint64_t` for sums, `OrderId = MatchId = uint64_t`. Plain type aliases.
**Options rejected:** a single 64-bit quantity type (bigger order objects for no benefit, since OUCH and ITCH carry 4-byte share counts); strong wrapper types such as `struct Price { int64_t v; }` (they prevent mixing a price with a quantity, but add a lot of boilerplate at this stage; `-Wconversion`/`-Wsign-conversion` catch the most dangerous mixes).
**Reason:** Order quantity matches the wire protocols. Totals over many orders cannot overflow (a test rests four `UINT32_MAX` orders at one price).

## D-014 (2026-11-18): Reference book from standard containers
**Choice:** `std::map<Price, Level>` per side (bids with `std::greater<>`, so `begin()` is best on both sides), a `std::list` FIFO per level, and an `std::unordered_map<OrderId, Location>` index storing side, price and list iterator.
**Options rejected:** a sorted `std::vector` of levels (cache-friendly, but O(L) insertion of a new price; a performance concern for Phase 3); `std::deque` per level (no O(1) erase in the middle, so cancels would shift elements).
**Reason:** Each container's guarantees map directly to an exchange rule: sorted prices give price priority, list order gives time priority, and stable list iterators give O(1) cancel without disturbing queue position.

## D-015 (2026-11-18): All outcomes are events with a fixed ordering contract
**Choice:** The book reports everything (accept, reject, trade, cancel, cancel-reject, level update) through `OrderBookListener` virtual callbacks, in the order documented in `events.hpp`. Methods return `void`.
**Options rejected:** return codes plus separate callbacks (two sources of truth); a templated listener (faster, but premature before measuring in Phase 4).
**Reason:** One stream feeds the gateway, the market data feed and the journal, and lets the Phase 3 fast book be verified by exact stream comparison. The listener must not re-enter the book.

## D-016 (2026-11-18): Order ID uniqueness is per resting order
**Choice:** The book rejects an ID only while an order with that ID rests; IDs of filled or canceled orders may be reused. A cancel for a filled order is `CancelRejected(UnknownOrderId)`.
**Reason:** Remembering every ID ever seen grows memory without bound. Day-long uniqueness per session belongs in the gateway (Phase 6).

## D-017 (2026-11-18): Model-based testing against a naive oracle
**Choice:** Besides scenario tests, randomized workloads run against both `MapOrderBook` and `tests/book/naive_book.hpp` (one flat vector, linear scans, no shared code), asserting identical event streams and invariants after every operation.
**Reason:** Random operation sequences reach combinations nobody writes by hand. Verified non-vacuous by mutation: a planted LIFO bug and a planted `<` vs `<=` crossing bug were each caught (8 and 17 failing tests).

## D-018 (2026-11-18): Hand-written exercises live outside the repository
**Choice:** Each phase's practice function lives in `exercises/phase-N/` (gitignored). Its tests carry the ctest label `exercise`, are excluded from every normal test preset, and run via `ctest --preset exercises`. Project code never depends on exercise code (for example, the project uses `std::bit_ceil`, not the exercise's `next_power_of_two`).
**Reason:** Unfinished exercises must never break CI or block the next phase, and exercises can be done at any time.

## D-019 (2026-11-18): Order entry through an `OrderRequest` struct
**Options:** (1) Keep growing `add_limit(id, owner, side, price, qty, type, tif, post_only)`. (2) One struct with named fields.
**Choice:** `submit(const OrderRequest&)` with designated initializers at call sites; `add_limit` removed.
**Reason:** Eight positional integer-like arguments make silent swaps (price for quantity) easy. Named fields are self-documenting, adding a field does not break callers, and the struct mirrors the Phase 5 "enter order" message.

## D-020 (2026-11-18): Order type semantics
- **Market:** no price limit (implemented as an extreme limit so every price crosses); never rests. `GoodTillCancel` on a market order behaves like IOC. `OrderAccepted.price` is 0.
- **IOC / FOK:** an unfillable remainder or an unfillable FOK is `OrderAccepted` then `OrderCanceled(Unfilled)`. A reject is reserved for invalid requests.
- **Post-only:** rejected with `PostOnlyWouldCross` if it would trade on arrival, checked against any resting order including the same owner's. Rejected over "sliding" to a non-crossing price for simplicity and explicitness. Only valid with Limit + GTC (`InvalidOrderType` otherwise).
- **Validation order** (first failure wins, identical for every book): zero qty, invalid type combination, off-tick price (limit only), odd lot, duplicate ID, post-only cross.

## D-021 (2026-11-18): Modify semantics
**Choice:** `modify(id, new_price, new_qty)`, where `new_qty` is the new *remaining* quantity. Priority is kept only if the price is unchanged and the quantity does not increase (shrink in place). Otherwise the order is removed (event `OrderModified{kept_priority=false}` plus the old level's update) and re-entered as a GTC limit order, so it may trade immediately. Post-only orders cannot be modified into a cross. Invalid modifies emit `ModifyRejected` and change nothing.
**Reason:** Keeping priority on a shrink harms nobody behind the order; anything else is equivalent to a new order. "Remaining" is unambiguous for partially filled orders.

## D-022 (2026-11-18): Self-trade prevention
**Choice:** An `owner` field on every order (`kNoOwner` = 0 is exempt) and one book-wide `SelfTradePolicy`: CancelNewest (default), CancelOldest, CancelBoth, Decrement. STP actions are reported as `OrderCanceled(SelfTradePrevention)`; Decrement reports partial cancels via `remaining_qty > 0`. STP also applies when a modify re-enters an order.
**FOK interaction:** a FOK is killed if a same-owner order lies within the quantity it would need, so a FOK never partially executes and never triggers STP.
**Reason:** Covers the policies real venues offer. Exempting owner 0 keeps anonymous flow (and the Phase 1 tests) unaffected.

## D-023 (2026-11-18): Tick and lot size live in `BookConfig`
**Choice:** Prices remain integers in the system's smallest unit; `BookConfig::tick_size` and `lot_size` are per-instrument multiples checked with `%`. Invalid configs (tick or lot < 1) throw `std::invalid_argument` from the constructor, at startup and never on the hot path.
**Reason:** Separates "the unit prices are expressed in" from "which prices this instrument allows", as real venues do. `x % m == 0` is correct for negative `x` in C++.

## D-024 (2026-11-18): Coverage assertions in the model test
**Choice:** Each random workload counts the events and paths it produced (trades, STP actions, priority-keeping vs priority-losing modifies, each reject reason) and fails if a path it should cover never occurred.
**Reason:** A random test that never reaches a rule passes vacuously. The first run proved the point: priority-keeping modifies occurred 0 to 7 times per 20,000 operations because random prices rarely matched the order's own price. The generator now targets each order's last known price half of the time.

## D-025 (2026-11-18): Common book interface as a C++20 concept (static polymorphism)
**Options:** (1) An abstract base class `OrderBook` with virtual `submit`/`cancel`/`modify`. (2) A concept `OrderBook<Book>` that both books satisfy; generic code is a template.
**Choice:** (2), in `order_book.hpp`, checked with `static_assert` next to each book. The shared tests are GoogleTest typed tests over `BookTypes = {MapOrderBook, FastOrderBook}`.
**Reason:** Calls are resolved at compile time and can be inlined; a virtual call is an indirect branch per operation and blocks inlining. Nothing needs to pick a book at run time. The listener stays virtual for now (one indirect call per event); Phase 4 measures whether that matters.

## D-026 (2026-11-18): Price band and capacity are book rules, enforced by every book
**Choice:** `BookConfig` gains `min_price`/`max_price` (limit prices outside: `PriceOutOfRange`, checked after the tick check and before the lot check, for submit and modify) and `max_orders` (a remainder that would rest in a full book: `OrderCanceled(BookFull)` after any trading). Defaults are unbounded, so existing users of `MapOrderBook` see no change. All three books (naive, map, fast) implement both, so the differential tests cover them.
**Rejected:** limits known only to `FastOrderBook` (the books would then disagree on those inputs and the differential test could not cover the paths); rejecting new orders up front when the book is full (a full book could then not even accept orders that would trade and free space).
**Note:** an order that trades never ends up `BookFull`: having a remainder means every order it crossed was used up, which freed at least as many slots as it needs.

## D-027 (2026-11-18): `FastOrderBook` layout
**Choice:** per side, a flat array with one level per tick in the band plus an occupancy bitmap; an index-based pool of 32-byte order nodes with intrusive doubly linked FIFO lists per level; a fixed-capacity open-addressing hash map (`FlatIdMap`) from order ID to node. All sized in the constructor from `BookConfig`; the constructor throws for an unbounded or too-wide band (more than 2^22 levels), a band not on tick, or `max_orders` above 2^24.
**Rejected:** a tree of levels (O(log n), node per level); `std::list` per level (allocation per order, scattered memory); `std::unordered_map` (a node allocation per insert); a direct array indexed by order ID (client IDs are sparse and reused).
**Details:** 32-bit indexes instead of pointers (half the size, survive moves, checkable). LIFO free list (reuses cache-warm slots). Best price moves to the next occupied level 64 levels per step via `countr_zero`/`countl_zero`; a two-level bitmap would bound that further and is not needed yet. `FlatIdMap` uses Fibonacci hashing (replaced by a fold in D-039), at most 50% load, and backward-shift deletion (no tombstones).

## D-028 (2026-11-18): Proving "no allocation after startup"
**Choice:** a separate test executable replaces the global `operator new`/`delete` with counting versions, arms the counter around replaying every standard workload into a `FastOrderBook`, and requires zero. Positive controls: a test that the counter sees an allocation, and a test that `MapOrderBook` does allocate. Not built under TSan (Clang's static TSan runtime defines `operator new`, so it cannot be replaced; the test is single-threaded anyway).
**Reason:** A rule that is only reviewed, not tested, regresses silently.

## D-029 (2026-11-18): Differential testing in two layers
**Choice:** (1) The model test replays each workload into the naive oracle, `MapOrderBook` and `FastOrderBook`, comparing events and queries after every operation (20,000 operations per workload; each workload's band is its generated price range plus a 10-tick margin so the per-operation invariant check stays cheap). (2) A long test compares only `FastOrderBook` with `MapOrderBook` on streamed operations (default 100,000 per workload, `LITBOOK_DIFF_OPS` for more), checking invariants every 4,096 operations.
**Reason:** The naive oracle is O(n) per operation, so it cannot run millions of operations; the map book is trusted because it matches the oracle.

## D-030 (2026-11-19): Differential fuzzing with fixed-size records, replayed in every build
**Choice:** one libFuzzer target (`fuzz/book_fuzzer.cpp`) that decodes its input as a 6-byte config header (tick, lot, band, capacity, self-trade policy) followed by 5-byte operation records, runs them through the naive oracle, `MapOrderBook` and `FastOrderBook`, and aborts on any difference in events, best prices, depth, counts or invariants. Value ranges are deliberately narrow (IDs 1..32, at most 32 orders, prices up to 4 ticks outside the band). Built only by the Clang `fuzz` preset (ASan + UBSan, `-O1`). The same `run_one` function is linked into `litbook_fuzz_replay`, a ctest test that replays `fuzz/seeds/` and `fuzz/regressions/` in every preset. CI runs the fuzzer for 60 seconds per push.
**Rejected:** `FuzzedDataProvider` (reading a variable number of bytes per value means one mutated byte shifts every later value, so mutations rarely keep a useful prefix); fuzzing each book alone for crashes only (it would miss wrong-but-not-crashing results, the more likely bug); committing the generated corpus (large and churns; `fuzz/corpus/` stays local).
**Reason:** random tests explore what the generator was written to produce; a coverage-guided fuzzer keeps inputs that reach new code and so finds paths the generator's probabilities make rare.

## D-031 (2026-11-19): First benchmark method
**Choice:** Google Benchmark (`bench/book_bench.cpp`), every benchmark instantiated for both books with the same config. A counting listener (one virtual call per event, no storage). Microbenchmarks run against a 2,000-order background book and restore its state each iteration; stream benchmarks replay a pre-generated test-generator stream into a fresh book, built and destroyed while the timer is paused. Results are recorded with 5 repetitions (median and coefficient of variation), release preset, in `docs/BENCHMARKS.md`.
**Reason:** these are relative, regression-tracking numbers. Tail latency (percentiles per operation) and the real-data headline benchmark (a full Nasdaq TotalView-ITCH 5.0 day) come in Phase 4, which needs a latency recorder and an ITCH parser first.

## D-032 (2026-11-19): The latency timer reads the CPU counter directly
**Choice:** `TickClock` (`include/litbook/metrics/tick_clock.hpp`) reads `cntvct_el0` on arm64 (with an `isb` barrier) and `rdtsc` on x86-64, and falls back to `steady_clock` elsewhere. On arm64 the tick length comes from `cntfrq_el0`. On x86-64 it is measured against `steady_clock` for 20 ms on first use. Histograms record raw ticks, which are converted to nanoseconds only when printed.
**Measured on M1:** the counter runs at 24 MHz, so one tick is 41.67 ns. Two back-to-back reads differ by 0 ticks 64% of the time. Book operations take about 12 to 35 ns (BENCHMARKS, Phase 3b), so a single operation usually measures as 0 or 1 tick.
**Consequence:** on this machine, percentiles up to about p99 cannot tell the books apart. The tool marks every value of at most 2 ticks. The tail (p99.9 and above) is where the books differ, and it is well above the tick. An x86 Linux machine (where `rdtsc` ticks well under 1 ns) is the planned second benchmark machine for finer numbers.
**Rejected:** `steady_clock` everywhere (on arm64 Linux it reads the same counter through the vDSO, with more overhead and no better resolution); the ARM cycle counter `PMCCNTR_EL0` (not readable from user space unless the kernel enables it, which Docker Desktop's VM does not).

## D-033 (2026-11-19): A log-linear latency histogram written in-house
**Choice:** `LatencyHistogram` (`include/litbook/metrics/latency_histogram.hpp`) works like HdrHistogram. Values 0..63 are counted exactly, and every power-of-two range above that is split into 32 buckets, so the error is at most 1/32 (about 3%). It is a fixed array of about 1,200 counters, recording costs a few instructions and never allocates, and two histograms can be merged. Percentiles round up to the top of the bucket (never below the true value) and are capped at the exact max. `record_corrected` adds the samples that coordinated omission hides, the same way HdrHistogram does.
**Bug found while writing the exercise tests:** the percentile rank was computed as `ceil(p / 100 * count)` in floating point. With 100 samples, `7 / 100.0 * 100` is 7.000000000000001, so p7 returned the 8th value; with 999 fast samples and one slow one, p99.9 returned the slow one. The rank is now computed with integers (percent rounded to parts per billion). Regression test `DecimalPercentilesUseTheExactRank`.
**Rejected:** storing every sample and sorting (8 bytes per sample is too much for a full ITCH day of about 270 million messages, and it allocates); the HdrHistogram C library (a new dependency for about 150 lines of code).

## D-034 (2026-11-19): How per-operation latency is measured and reported
**Choice:** `litbook_latency` (`bench/latency_main.cpp`) generates each stream up front, runs one untimed warm-up pass and 5 timed passes per book and workload, each into a fresh book, and times every operation. Each printed percentile is the **median over the 5 passes**, and the max is the largest of any pass. It also prints the timer's own cost and the p99.9 spread over passes. Workloads come from `MarketGenerator` (`bench/market_workload.hpp`), which only sends valid orders, places them near the best price with geometrically decreasing distance, lets the price drift, and steers the cancel rate so the book settles at a target size (2,000 or 20,000 orders).
**Reason:** merged histograms were dominated by single passes the VM had interrupted (p99.99 moved by 10x between runs); the median of passes was stable across invocations. An earlier version of the generator only canceled the last 4,096 orders, so the book grew for the whole run, which is unlike a real book; the target size fixes that.
**Note:** these are service times (one call to the book, listener calls included), measured back to back with no target rate, so coordinated omission does not apply. End-to-end latency under an offered load comes with the gateway in Phase 7.

## D-035 (2026-11-19): Read ITCH as a stream, decode with a compile-time handler
**Choice:** `BinaryFileReader` splits Nasdaq's BinaryFILE format (2-byte big-endian length, then the payload, and a zero-length message at the end of the session) from any `FILE*`, through one buffer allocated in the constructor. Real days are replayed as `gunzip -c day.gz | tool`, so the 8.25 GB uncompressed file never touches the disk. `parse_message` decodes one payload into a struct and calls a handler that is a template parameter (checked by the `ItchHandler` concept). Every known type must have exactly the length in the specification, or it is reported as `BadLength` and not passed on. Types that do not change a book are skipped.
**Rejected:** decompressing in-process with zlib (a new dependency), decompressing to disk first (the development disk had about 16 GB free), virtual handler methods (one indirect call per message for no benefit), reading fields by casting the bytes to packed structs (alignment and endianness problems, undefined behavior).
**Checked against the real file:** 268,744,780 messages on 2019-12-30 with zero wrong lengths, zero references to unknown orders and zero duplicate references.

## D-036 (2026-11-19): A third book, SortedOrderBook, because real data breaks the ladder
**Context:** `FastOrderBook` (D-027) needs a price band with at most 2^22 ticks. On the real Nasdaq day, most stocks have market-maker stub quotes at $0.0001 and $199,999.99, so 6,932 of 8,892 stocks span more than 2^22 levels even at a 1-cent tick, and only 1,611 fit a 16,384-level ladder. Real orders still cluster near the market (98.97% of new orders land within $20.47 of the stock's last trade).
**Choice:** keep `FastOrderBook` unchanged and add `SortedOrderBook`, which has the same rules and the same event stream. Per side it keeps a sorted array of {price, level slot} from the worst price to the best, so the busy end is the back of the array. Finding a price checks the last 8 entries and then binary searches. Levels live in a pool, so orders point at a stable slot and shifting the array never breaks them. Orders, the FIFO lists and the ID index are the same as in `FastOrderBook`. Both arrays reserve `max_orders` entries, so nothing allocates after construction. It needs no band.
**Rejected:** replacing the ladder inside `FastOrderBook` (loses a design that is right for venues that enforce price collars, and the comparison); a dense window around the market plus an overflow structure (fastest lookups but the most complex, with re-centering and about 14 GB for all stocks unless sized per stock; a candidate for Phase 4c); replaying with `MapOrderBook` only.
**Testing:** joins every typed scenario, the four-way model test, the differential test, the fuzzer and the no-allocation test, plus its own tests. Of 5 planted bugs, 4 were caught and the fifth was an equivalent mutant (searching `[0, i - 1)` instead of `[0, i)` when entry `i - 1` is already known to be better).

## D-037 (2026-11-19): How a real ITCH day is replayed and measured
**Choice:** `ItchBookBuilder` turns ITCH into book calls: an add is a resting limit order, an execution or partial cancel is a modify to the smaller size (which keeps priority) or a cancel when nothing is left, a delete is a cancel, and a replace is a cancel followed by a new order on the same side. It keeps its own record per resting order in a fixed `IndexPool` plus `FlatIdMap`. Books are sized per stock from a first pass (`litbook_itch_stats` writes each stock's peak resting orders and price range), with 50% slack. `litbook_itch_replay` times only the calls into the book, one sample per ITCH message, and reports a health check: because Nasdaq already matched everything, a faithful replay has zero trades and zero rejects, and every book replayed all day ends empty.
**Halts:** the first verify run found 1,577 trades in 15 stocks, every one while the stock was halted, paused or in a quotation-only period. Nasdaq accepts orders then without matching and clears the crossed book with a reopening auction; our books always match and have no auctions. The builder therefore stops replaying a stock at its first trading action that is not 'T', for the rest of the day (24 of 8,892 stocks on 2019-12-30). Modeling auctions would be its own phase.
**Correctness on real data:** `verify` mode runs `MapOrderBook` and `SortedOrderBook` side by side; on 2019-12-30 their events matched for all 263,116,612 messages that reached a book, with zero trades, rejects, drops or invariant failures.
**Note:** this measures maintaining a book from a feed (adds, cancels, reductions), as CppTrader's published ITCH benchmark does, not matching. Matching cost is covered by the synthetic benchmarks (Phase 3b, 4a).

## D-038 (2026-11-19): Profiling with perf inside the Docker VM
**Choice:** the dev image installs `linux-perf` (Debian/Ubuntu's single perf binary, not tied to a kernel version; `linux-tools-generic` ships no `/usr/bin/perf` for the linuxkit kernel), and the container runs with `--cap-add PERFMON`. A `profile` preset builds Release with `-g -fno-omit-frame-pointer -mno-omit-leaf-frame-pointer`, and `scripts/profile.sh` samples with `perf record -e cpu-clock --call-graph fp`.
**Why the workarounds:** Docker Desktop's VM exposes no hardware counters (no cycles, cache misses or branch misses), so only software events such as `cpu-clock` work. perf also cannot name functions on its own: the kernel reports the binary under the VM's internal path (`/run/host_virtiofs/...`) and a build ID with extra note-header bytes in front, so perf decides the file does not match. The script records raw addresses and resolves them with `addr2line`, which reads the DWARF information straight from the binary, then groups samples per function and caller.
**Rejected:** running perf on the macOS host (no perf on macOS; Instruments would profile a different OS and compiler), or a bare-metal Linux machine (not available; noted as future work for hardware counters).

## D-039 (2026-11-19): FlatIdMap folds the key instead of Fibonacci hashing
**Choice:** `home(key)` XORs the key's table-index-wide chunks together (`h = key; h ^= key >> b; h ^= key >> 2b; ...; h & mask`) instead of multiplying by 2^64/φ and keeping the top bits.
**Why:** the untimed profile of the full-day sorted replay put about 28% of samples in `FlatIdMap` operations (the book's cancel and validate lookups, and the builder's own table). Nasdaq hands out order reference numbers in increasing order, and most orders are canceled soon after they are added, so the IDs touched at any moment are close together. Fibonacci hashing scatters close IDs across the whole table (every lookup a likely cache miss); the fold keeps them in nearby slots that stay in cache. Every key bit still reaches the index, so keys that differ only in high bits do not all collide (unit tests check the longest probe for strides 2^10 to 2^32 and for sequential keys).
**Measured:** five A/B pairs on the same build, alternating the two binaries, full day, untimed, CPU time of the message loop. Fibonacci 63.7, 61.1, 78.2, 67.9, 64.6 s; fold 58.7, 57.7, 64.2, 60.8, 69.2 s. The fold won 4 of 5 pairs; medians 64.6 vs 60.8 s (about 6% of the loop, about 8% of the book's own share after the roughly 16.5 s null-book pipeline). Run-to-run noise on this VM is about as large as the gain (the same binary ranged from 57.7 to 75.4 s within one session), so this is a likely improvement, not a proven one; hardware counters on bare metal (cache misses per lookup) would settle it. Kept because it is no worse on any run set, has a clear mechanism, and passes the pile-up tests.
**Still the top hotspot:** a profile after the change (sampled timing, see D-040) puts about 44% of samples in `FlatIdMap` (find 16%, home 12%, slot reads 7%, erase 6%). Part of `home` is the fold loop itself, which cannot be unrolled because the table width is only known at run time. Follow-ups: a fold with a fixed number of steps, and a smaller per-stock table.
**Rejected:** keeping Fibonacci hashing (measurably slower); identity hashing (`key & mask`, which ignores high bits, so strided keys pile up); a stronger mixer such as murmur's finalizer (spreads keys like Fibonacci, which is what we want to avoid here). Not hardened against adversarial keys, which is fine for exchange-assigned IDs; revisit if client-chosen IDs ever reach this table.


## D-040 (2026-11-19): The replay times one message in 64, and reports the timer floor
**Problem:** `TickClock::now()` on ARM is `isb` followed by reading `cntvct_el0`. The barrier makes the CPU finish everything in flight first, so timing every message disturbed the very thing being measured. The profile of the every-message replay put about 54% of samples in `TickClock::now()`, and in back-to-back runs the message loop used 10 to 22 s more CPU timed than untimed (sorted 86.5 / 75.9 vs 64.7 / 65.4 s; map 132.6 / 135.5 vs 109.9 / 115.7 s), roughly 40 to 100 ns per message. The Phase 4b per-message numbers are therefore inflated by the measurement; those rows stay in BENCHMARKS.md with a note.
**Choice:** `litbook_itch_replay` times one message in N (default 64, `--sample-every N`; N = 1 is the Phase 4b method). It still gets about 4.1 million samples on the full day, enough for p99.99. Each sample still contains one timer read, so the tool also prints the timer floor (an empty call timed the same way; p50 0, p99 42 ns on M1). `--untimed` and a `null` book (the pipeline alone) give a second, timer-free view: an untimed real book minus the null book is the book's own CPU cost, an upper bound because cache sharing with the decoder is charged to the book.
**Measured:** with 1-in-64 sampling the profile shows 0.81% of samples in `TickClock::now()` (was about 54%).
**Rejected:** subtracting a fixed per-read overhead from every sample (the barrier's cost depends on what the book left in flight, so it is not a constant); timing batches of messages (gives an average, loses the tail, which is the point of percentiles); random sampling instead of every Nth (ITCH has no structure with period 64, so a fixed stride is simpler and reproducible).
**Caveat:** run-to-run CPU-time noise in this VM is large (the same binary ranged from 57.7 to 75.4 s in one session). Only compare CPU times from alternated A/B pairs.
## D-041 (2026-11-19): One book per stock, routed by a dense SymbolId
**Options:** (1) A hash map from ticker string to book, looked up on every call. (2) Dense 16-bit SymbolIds handed out at startup, with the books in an array and one flat hash table from ticker to SymbolId. (3) One book holding every stock.
**Choice:** (2). `Engine<Book>` is a template over the `OrderBook` concept. Each stock's book reports into a small forwarder that adds the SymbolId, and the forwarder replaces `Trade::match_id` with an engine-wide counter so match numbers are unique for the day across all stocks. Order IDs stay per book; making them unique is the order entry layer's job. Unknown SymbolIds return `EngineStatus::UnknownSymbol` and send no event, since no book is involved.
**Reason:** A ticker string hash and compare on every call is wasted work, and ITCH already uses a 16-bit locate code for the same idea, so the ticker is turned into an integer once at the edge. Option (3) would make every stock share one ladder and one capacity, and a bug in one stock could corrupt another. Each book is its own allocation (a `unique_ptr` to a slot holding the forwarder and the book) because the book keeps a reference to its forwarder, so the slot must never move.

## D-042 (2026-11-19): Wire codec with explicit big-endian fields at fixed offsets, modeled on OUCH 5.0
**Options:** (1) `#pragma pack` structs laid out like the wire, filled by `reinterpret_cast` or `memcpy` of the frame. (2) Plain C++ structs for decoded values, and a codec that reads and writes each field at a documented offset with byte-by-byte big-endian loads and stores. (3) A byte-exact OUCH 5.0 implementation including the TagValue appendage.
**Choice:** (2). Messages keep OUCH 5.0's type letters, field encodings (big-endian integers, prices with 4 implied decimals up to $199,999.9900, space-padded symbols, UserRefNum, cancel to an intended size) and session rules, but have fixed lengths and only the fields litbook supports. Every difference is listed in `docs/PROTOCOL.md`. The decoder returns a `DecodeStatus` and never throws or allocates. Inbound enumerated fields are checked strictly, outbound reason codes and liquidity flags are open sets, and every frame that decodes re-encodes to the same bytes. Malformed frames (bad bytes) are separate from rejected orders (well formed but breaking a trading rule).
**Reason:** Packed structs depend on the host's byte order, invite misaligned and type-punned access (undefined behavior that only shows up on some CPUs or compilers), and tie the in-memory type to the wire. The shift loop compiles to one load plus a byte reverse, so explicit fields cost nothing. Option (3) would mean parsing variable-length option lists for features the books do not have; it can be added later without changing the engine.
**Checked by:** golden frames written out field by field in the tests, every truncation and every unknown type byte, bad values in every enumerated field, and a `protocol_fuzzer` libFuzzer target (130 million inputs in a 2 minute local run, no failures; a planted bug that accepted a lowercase `y` flag was caught within 60 s).

## D-043 (2026-11-19): The order entry layer owns the engine and keeps one record per live order
**Options:** (1) Give the client's UserRefNum straight to the book as the order ID. (2) The exchange assigns its own day-unique Order Reference Number, uses it as the book order ID, and keeps a record per live order reachable from both (account, UserRefNum) and the reference number.
**Choice:** (2). `OrderEntry<Book>` owns the `Engine` and is its listener. Records live in an `IndexPool`, and two `FlatIdMap`s (key `owner << 32 | UserRefNum`, and reference number) point at them, so nothing allocates after startup. A record stores the shares executed so far, which OUCH's "intended size" cancels and replaces need. It is released as soon as the order has no open quantity. Because a listener may not call back into the engine, a cancel or replace sets a small `pending_` state before calling `modify`, the event handlers read it, and follow-up work (canceling the original after a failed replace) runs after the call returns.
**Rejected:** option (1), because UserRefNums are only unique per account, so two accounts would collide in one book, and the exchange could not give out day-unique reference numbers. Tracking executed shares in the book, because it is session state the book does not need.
**Details:** an invalid replace sends Rejected for the new UserRefNum and then cancels the original, as OUCH does with an invalid replace. A reducing cancel whose new size is not a multiple of the lot size is ignored and counted, because the book refuses it and the order does not change.

## D-044 (2026-11-19): The gateway speaks SoupBinTCP 3.0, and its rules live apart from the sockets
**Options:** (1) A bare 2-byte length prefix in front of each OUCH message. (2) SoupBinTCP 3.0, Nasdaq's session protocol for OUCH, with login, heartbeats, sequenced and unsequenced envelopes, logout and end of session. For where the rules live: (a) inside the epoll loop, or (b) in a `SessionManager` that never touches a socket and is driven by calls such as "this connection opened", "these bytes arrived", "the clock is now t", "this much output was written" and "the connection is gone".
**Choice:** (2) and (b). `include/litbook/gateway/soup.hpp` parses and builds packets without copying or allocating. `Session` holds one connection's protocol state and two fixed `ByteBuffer`s. `SessionManager<Book>` owns the `OrderEntry`, the accounts and a pool of sessions made at startup, and it is the order entry layer's `OutboundSink`. The Phase 6b epoll code only moves bytes between sockets and these calls.
**Reason:** SoupBinTCP is how OUCH actually travels, it is only ten small packet types, and it gives accounts, logins and heartbeats for free. Keeping the rules away from system calls means every rule is tested with plain byte arrays and a made up clock, including every two-way split of a byte stream and one byte at a time, and the whole layer can be fuzzed (`session_fuzzer`).
**Limits chosen where the specification is silent:** client packets longer than 47 bytes after the length field close the connection (checked as soon as the two length bytes arrive), one connection per account, and a requested sequence number ahead of the next one is accepted with the real next number. Replaying old sequence numbers is refused with Login Rejected `S` until the Phase 9 journal can regenerate them.
**Rejected:** a ring buffer per connection (it would split packets across the end of its memory; with packets of at most 50 bytes, moving the leftover bytes to the front is cheap and keeps every packet contiguous).
**Checked by:** a mutation check of 9 planted bugs in the session layer, buffers, codec and order entry changes (all caught, one as a hang by the test timeout), and a fuzzer run that caught a planted sequence-number bug within 60 seconds when started from the seeds.

## D-045 (2026-11-19): Backpressure first, disconnect only when the output buffer is full
**Problem:** the first version processed every byte it was handed. A client that sent 200 orders in one read produced 9,600 bytes of replies, overflowed its 4 KiB test output buffer, and was disconnected as a slow consumer although it was reading fine.
**Choice:** a connection's input is only processed while fewer than `output_high_water` bytes (32 KiB by default, out of 64 KiB) wait in its output. Past that, new bytes stay in the input buffer, `receive()` takes no more, and `receive_room()` is 0, so the network code stops reading that socket and TCP flow control slows the client down. `sent()` resumes processing. The space above the high water mark is for replies that cannot be held back (executions caused by other accounts, heartbeats). Only when those fill the whole buffer is the client disconnected with `OutputFull`.
**Rejected:** an output queue that grows without limit (a client that stops reading would use up the exchange's memory), and disconnecting at the first full buffer (punishes a client for sending a burst).
**Consequence:** a paused client that keeps sending but never reads stops being read, so it eventually hits the idle timeout. That is the behavior wanted for a client that does not read its replies.

## D-046 (2026-11-19): Risk checks and cancel on disconnect live in the order entry layer
**Choice:** `RiskLimits` per account (largest order quantity, most live orders) are checked in `OrderEntry` before an order reaches its book, and the quantity limit also applies to the new size in a Replace. An order over the size limit gets OUCH's own code 0x0031 (Risk: Max Quantity Exceeded). OUCH has no code for an open order limit, so that one is the litbook extension 0x0103. `OrderEntry::cancel_all(owner, now)` cancels every live order of one account, reported with cancel reason `Z` (system), because OUCH's `U` means "sent in response to a Cancel Request". To find one account's orders without scanning everyone's, each record is on a doubly linked list per account (two 32-bit indexes in the record), so `cancel_all` costs time proportional to that account's live orders and allocates nothing.
**Rejected:** checking risk in the gateway (it would have to rebuild the live order count per account by watching the replies, a second copy of state `OrderEntry` already has), and scanning the whole record pool on disconnect (time proportional to every live order on the exchange).

## D-047 (2026-11-19): A single-threaded, level-triggered epoll gateway
**Options:** (1) One blocking thread per connection. (2) One thread with epoll, edge triggered. (3) One thread with epoll, level triggered. (4) io_uring.
**Choice:** (3), `EpollGateway<Book>` in `include/litbook/gateway/epoll_gateway.hpp`. Each `poll_once()` accepts waiting connections (`accept4` with `SOCK_NONBLOCK`, `TCP_NODELAY` on), reads at most `receive_room()` bytes from each readable socket, runs `tick()` every 100 ms, then writes out every connection's output with `send(MSG_NOSIGNAL)` and closes the ones the session layer gave up on. A socket's `EPOLLIN` interest is off while its input is paused, and `EPOLLOUT` is on only while output is left over. `stop()` writes to an eventfd, so it is safe from another thread or a signal handler. The clock is a function pointer, so tests move time by hand.
**Reason:** a thread per connection needs a lock around the engine, and the lock then decides the order of orders. Edge triggering wakes the loop once per change, so every handler must read until `EAGAIN` or lose the wakeup, and pausing a client would need extra bookkeeping. Level triggering keeps telling the loop a socket is ready until it acts, and turning `EPOLLIN` off is the whole backpressure mechanism. io_uring support inside the Docker Desktop VM is uncertain and it is much harder to reason about. Writing every connection's output after each round is needed because one client's order can produce replies for many others. It costs O(connections) per round, which is fine for the 64 connection default; a list of connections with new output would bound it if that ever measures as a cost.
**Rejected details:** waiting for `EPOLLOUT` before every write (one extra system call and wakeup per reply; the gateway writes straight away and only falls back to `EPOLLOUT` when the kernel buffer is full), and letting a closing session linger until its output drains (a client that stops reading would keep the slot; one write attempt is made, then the socket closes).
**Checked by:** 16 integration tests over loopback sockets (many clients, one byte at a time, malformed input, rejected login delivered before the close, cancel on disconnect, connection limit, heartbeats and idle timeout on a fake clock, end of session, a burst that pauses a client without dropping it, a slow reader dropped with small kernel buffers, a threaded run for TSan), a no-allocation test over real sockets (20,000 frames), end-to-end tests of the `litbook_gateway` program, and 4 planted bugs (all caught, one as a hang).


## D-048 (2026-11-20): Cache line padding of 128 bytes, set by hand
**Options:** (1) `std::hardware_destructive_interference_size`. (2) 64, the line size Linux reports. (3) A project constant of 128.
**Choice:** (3), `kCacheLineSize` in `include/litbook/concurrency/cache_line.hpp`.
**Reason:** the three sources disagree on the development machine. Inside the Docker VM, `getconf LEVEL1_DCACHE_LINESIZE` and the CTR_EL0 register both say 64 bytes. The macOS host says `hw.cachelinesize: 128` for the same Apple M3 Pro. GCC 15.2 and Clang 21.1 both define `hardware_destructive_interference_size` as 256 on 64-bit ARM. That constant can also change with `-mtune` or the compiler version, so two files built with different flags could disagree about a struct's layout, and GCC warns (`-Winterference-size`, an error under `-Werror`) when it is used in a header. On x86-64 lines are 64 bytes, but Intel's L2 spatial prefetcher fetches each line together with its pair to fill a 128-byte aligned block, so variables 64 bytes apart can still interfere. 128 is safe on all of these and costs a few hundred bytes per queue.

## D-049 (2026-11-20): A bounded lock-free SPSC ring with cached indexes
**Options:** (1) A queue under a mutex. (2) A lock-free multi-producer multi-consumer queue. (3) A single-producer single-consumer ring with two counters on separate cache lines, each side keeping a private copy of the other side's counter (the design of Erik Rigtorp's SPSCQueue). (4) The same ring without the private copies.
**Choice:** (3), `SpscQueue<T>` in `include/litbook/concurrency/spsc_queue.hpp`. The capacity is a power of two and the slots are allocated once in the constructor, with one cache line of unused slots at each end so neighboring heap data cannot share a line with the first or last slot. The counters are 64-bit and only grow, so a full queue (`tail - head == capacity`) and an empty one (`tail == head`) are told apart without wasting a slot, and they would take centuries to wrap. A push writes the slot and then stores `tail` with release. The consumer loads `tail` with acquire, so it sees the finished slot. A pop reads the slot and then stores `head` with release, and the producer loads `head` with acquire before reusing the slot. Nothing stronger than acquire and release is used. Elements must be trivially copyable (the `QueueElement` concept), so nothing is allocated when a message moves. `front()` and `pop()` let the consumer read a message in place.
**Reason:** litbook's pipeline has exactly one writer per queue (one gateway thread, one matching thread), so the locks or compare-and-swap loops a multi-producer queue needs are pure cost. Without the private copies (option 4) every push reads `head` and every pop reads `tail`, which pulls the other core's cache line over on every message even when the queue is half full. With them, a push or pop on a queue that is neither full nor empty touches no line the other thread writes.
**Checked by:** single-threaded tests of empty, full, FIFO order, wrap around at every offset and stale private copies, two-thread stress tests at capacities 1 to 1024 that check order and torn messages and assert that both the full and the empty path ran, a ping-pong test, all of them under ThreadSanitizer in the tsan presets, and a no-allocation test.

## D-050 (2026-11-20): A mutex queue with the same interface, kept as the baseline
**Choice:** `MutexQueue<T>` (`include/litbook/concurrency/mutex_queue.hpp`) is a bounded ring under one `std::mutex` with two condition variables. It has the same `try_push`, `front`, `pop`, `try_pop`, `capacity` and `size_approx` as `SpscQueue`, checked by the `MessageQueue` concept, plus `push_wait` and `pop_wait`, which sleep instead of failing. Tests, benchmarks and the Phase 7b pipeline are templates over the queue type, so the comparison changes nothing but the queue. `litbook_queue_latency` measures three setups: SPSC spinning, the mutex queue spinning on its `try_` calls (only the lock differs), and the mutex queue sleeping on its condition variables (the usual way it is written).
**Also added:** `pin_current_thread`, `allowed_cpus` and `current_cpu` (`include/litbook/concurrency/thread_affinity.hpp`) around `pthread_setaffinity_np` and `sched_getaffinity`. They were checked to work inside the Docker VM, where a pinned thread stays on one virtual CPU but macOS still chooses the physical core under it.
**Rejected:** comparing against a mutex queue written only inside the benchmark (it would not be tested, and a slow comparison queue proves nothing).

## D-051 (2026-11-20): The session layer sits on a pluggable order backend, and counts requests in flight
**Options:** (1) A second session manager written for the threaded pipeline. (2) A runtime switch inside `SessionManager` that sends orders either to its own order entry layer or to a queue. (3) `BasicSessionManager<Backend>`, a template over an `OrderBackend` concept.
**Choice:** (3), in `include/litbook/gateway/order_backend.hpp` and `session_manager.hpp`. A backend offers `forward(owner, frame, now)` (Taken, Malformed or Busy), `cancel_all`, the startup calls, and `kAsynchronous`. `InlineBackend<Book>` owns `OrderEntry` and answers on the calling thread, which is exactly Phase 6, and `SessionManager<Book>` is now an alias for `BasicSessionManager<InlineBackend<Book>>`, so no Phase 6 caller changed. `pipeline::QueueBackend` pushes onto the matching thread's queue instead. Its replies come back through `deliver()`, and every order request ends with `request_done()`.
**Backpressure (extends D-045):** with an asynchronous backend the output buffer no longer shows how many replies are still coming, so each account counts its requests in flight. The next packet is forwarded only while the output plus one reply's worth of room (50 bytes) per request in flight stays below `output_high_water`, and while fewer than `max_in_flight` (default 64) are in flight. With the inline backend the count is always 0 at that check, so the rule is exactly the Phase 6 rule. A full request queue (Busy) leaves the packet in the input buffer, and `retry_waiting()` offers it again after the next drain of replies, so the gateway thread never waits for the matching thread.
**Cancel on disconnect:** `close()` asks the backend to cancel the account's orders. If the queue is full, the account is marked `cancel_pending`, its input (on a new connection too) is held back, and `retry_waiting()` queues the cancel before any later order of that account. Otherwise a new order could overtake the cancel and be canceled by it.
**Rejected:** (1) duplicates every session rule and the 6a tests and fuzzer would cover only one copy. (2) would leave an unused order entry layer (tens of megabytes of tables) inside the threaded gateway. Reserving room without a "request done" signal was also rejected, because a request can produce zero replies or many.
**Checked by:** all 736 Phase 6 and 7a tests unchanged, 13 session tests over a fake asynchronous backend (in-flight count, the 50-byte reservation, the in-flight cap, busy retry order, a deferred cancel that goes before the account's next order), and a test that feeds one random 4,000-frame stream into the inline gateway and the hand-driven pipeline and requires byte-identical output on every connection. A mutation check of the pipeline caught 14 of 15 planted bugs (one only through ThreadSanitizer, five as hangs). The survivor removes the shutdown loop that waits for deferred cancels, which only matters if Stop finds room in the queue before a deferred cancel is retried.

## D-052 (2026-11-20): Three threads, raw frames in fixed-size messages, and a matching thread that never drops
**Choice:** `pipeline::ThreadedGateway<Book, Queue>` (`include/litbook/pipeline/`). The gateway thread runs the epoll loop and the session layer and both reads and writes the sockets. The matching thread (`MatchingWorker`) owns `OrderEntry` and every book. The publisher thread (`PublisherStub`) counts the trades and level updates it receives (it becomes the market data feed in Phase 8 and the journal writer in Phase 9). They are connected by three single-producer single-consumer queues of `Request`, `Reply` and `MarketEvent`, each a trivially copyable struct of at most 64 bytes. A request carries the owner, a timestamp taken by the gateway, and the raw OUCH bytes. The gateway decodes each frame once to check it, so a malformed frame still closes the connection before any later packet of that client is forwarded, and the matching thread decodes it again. Every Frame request ends with one RequestDone reply. When the reply or event queue is full, the matching thread rings the consumer's doorbell and spins until there is room; it never drops a message. This cannot deadlock because the gateway and the publisher never wait for the matching thread. Shutdown travels as a Stop request, so it is handled after everything queued before it, and the gateway keeps draining replies until the matching thread answers Stopped.
**Rejected:** the publisher thread writing client sockets (two threads would share the session buffers); decoded messages in the queue (a `Ticker` has no default value, so the variant cannot be a queue element, and Phase 9 wants the raw inbound bytes for the journal); decoding only on the matching thread (packets after a bad frame would already be forwarded when the gateway heard about it); dropping replies when the queue is full (they already have sequence numbers); waking consumers once per message instead of once per request.
**Consequence:** the gateway sets every timestamp, so the matching thread reads no clock and the order of the request queue alone decides what happens, which is what the Phase 9 journal needs. An order now crosses two extra thread hops, so the closed-loop round trip may get slower than Phase 6. The gain is that socket work no longer runs on the thread that owns the books.

## D-053 (2026-11-20): A doorbell with one atomic state and an eventfd for the blocking mode
**Options:** (1) A mutex and condition variable per queue. (2) A "sleeping" flag plus `std::atomic_thread_fence(seq_cst)` on both sides (the Dekker pattern). (3) One atomic state with three values (Awake, Sleeping, Rung) changed only by atomic exchange, plus an eventfd.
**Choice:** (3), `pipeline::Doorbell` (`include/litbook/pipeline/doorbell.hpp`). A producer pushes and then exchanges the state to Rung, and writes the eventfd only if the old state was Sleeping. A consumer that found its queue empty exchanges the state to Sleeping; if the old state was Rung it looks at the queue again instead of sleeping. All exchanges of one variable happen in one total order, so for any push the consumer missed, either the consumer sees Rung or the producer sees Sleeping, and no wakeup is lost. While the consumer is awake a push costs one atomic exchange and no system call. The gateway thread watches the reply doorbell's eventfd in its own epoll set. The matching and publisher threads sleep in `poll()` on theirs, with no timeout, so a lost wakeup would hang the tests instead of hiding as a delay.
**Rejected:** (1) the gateway thread already sleeps in `epoll_wait` and cannot also wait on a condition variable, and a different wait mechanism per queue type would spoil the SpscQueue against MutexQueue comparison (D-050). (2) GCC's ThreadSanitizer does not support `atomic_thread_fence` (it warns, which `-Werror` makes fatal, and it cannot check the fences), and a seq_cst store followed by an acquire load is not ordered by the C++ memory model without one.
**Checked by:** single-threaded state tests, a ring from another thread, and a stress test where the consumer sleeps with no timeout every time its queue is empty (50,000 messages, it must sleep and be woken more than 10 times), all under ThreadSanitizer; blocking variants of every threaded pipeline test.

## D-054 (2026-11-21): Time inside the gateway is sampled by the session layer
**Options:** (1) Stamp a send time into every `Reply` and compute the time when the gateway thread drains it. (2) Time from outside only, with the client's round trip. (3) Let the session layer time one order in N (`SessionConfig::sample_every`), from handing it to the backend until every reply is in the output buffer.
**Choice:** (3). With the inline backend a sample is the `forward()` call. With an asynchronous backend the sample ends at the order's `RequestDone`. Requests of one account finish in the order they were sent, so the session layer stores how many requests of that account were in flight and counts them down. Only one sample runs at a time. It is off by default (0), and `litbook_gateway_latency` uses 1 in 16.
**Rejected:** (1) makes every reply bigger and changes the matching thread only for a benchmark. (2) cannot separate what the pipeline adds from the two kernels' loopback paths and the client's wakeup.
**Checked by:** six session layer tests (off by default, a sample ends at its own RequestDone and not another account's, one in N, busy and malformed orders are not sampled, the inline backend samples each forward).

## D-055 (2026-11-21): A market by price feed in MoldUDP64 packets, with a snapshot stream for recovery
**Options:** (1) ITCH 5.0 order messages in MoldUDP64 packets, a market by order feed. (2) litbook's own price level messages in MoldUDP64 packets, plus a second stream of snapshots. (3) A TCP connection per subscriber.
**Choice:** (2), specified byte by byte in `docs/FEED.md`. The packet layer follows Nasdaq's MoldUDP64 1.00 (20-byte header with session, the first message's sequence number and a message count; 0 is a heartbeat and 0xFFFF is end of session). The messages are System Event, Symbol Directory, Price Level Update (the new total of a level), Trade, Snapshot Start and Snapshot End, with ITCH style fixed offsets and 8-byte timestamps. The snapshot stream repeats every stock's levels, and each snapshot says which incremental sequence number it is as of, so a receiver that lost packets or joined late can line it up with the incremental messages it buffered. The specification leaves the session name padding, the first sequence number and the packet size to the sender. litbook pads on the left, starts at 1 and sends at most 1,200 bytes of UDP payload.
**Rejected:** (1) needs an event for every order change from the matching thread instead of the level totals it already sends, and the ITCH parser of Phase 4b already covers reading per order data. (3) lets one slow subscriber back up the publisher and sends every message once per subscriber, which is why exchanges publish over multicast. A MoldUDP64 re-request server for missed messages is left for later, because snapshots already cover both late joiners and gaps with one mechanism. The cost is that trades lost in a gap cannot be recovered.
**Recovery is per stock.** A gap makes every stock stale, because a lost packet could have been about any of them. Each stale stock remembers the first sequence number it buffered (`needs_from`), and each live stock the last number its book includes (`through`). A snapshot is used only if it includes everything before `needs_from`, and later messages up to `through` are skipped, so a snapshot that is older or newer than the incremental stream both work. A single "first buffered message" for the whole feed was the first idea and is wrong: a stock that went stale later (its book was full) would then accept a snapshot older than its own missing updates. Snapshot Start carries the number of stocks, so a late joiner knows when it has them all.
**Consequence:** a Price Level Update carries the new state of a level, so applying it twice is harmless and a snapshot can be built from the same messages. Incremental messages take their timestamp from the inbound request, so the incremental stream depends only on the request order (Phase 9). `MarketEvent` gained a `now` field for that, filled by the matching thread from the request it is handling.
**Checked by:** golden frames for every message and packet type; publisher tests for packing, splitting, snapshot content and `as_of`, heartbeats and end of session; handler tests for every recovery path (late snapshot with replay, too old, newer than the stream, snapshot stream gap, buffer overflow, heartbeat gap, late join, overlapping packets); five end to end runs where random orders go through the real books and the packets cross a channel that drops, duplicates, reorders and delays them, which must end with the handler, the publisher's copy and the engine's books identical (and in step during the run whenever nothing is missing); a no-allocation test of the whole path; and `feed_fuzzer`, which also checks recovery differentially.

## D-056 (2026-11-22): Multicast sockets that name their interface, hear only their own group, and never block the publisher
**Choice:** `feed::MulticastSender` and `feed::MulticastReceiver` (`include/litbook/feed/multicast.hpp`). Both sides name the network interface (`lo` in tests, any interface for `litbook_gateway --feed`) and pass it to the kernel by index in an `ip_mreqn`, for `IP_MULTICAST_IF` on the sender and `IP_ADD_MEMBERSHIP` on the receiver. The sender is non-blocking and `connect()`ed to the group, so each packet is one `send()` with no address, and a full kernel buffer drops the packet and counts it (`SendOutcome::Dropped` for EAGAIN, EWOULDBLOCK and ENOBUFS) instead of stalling the publisher thread. TTL is 1, so packets never leave the local network. A receiver sets `IP_MULTICAST_ALL` to 0 and binds to the group address itself, with `SO_REUSEADDR` so that several receivers on one host can share a port. It reads with `MSG_TRUNC` into a 2,048-byte buffer, so a packet that is too long shows up as Truncated instead of as a shorter packet.
**Measured first, in the container:** `lo` does not have the MULTICAST flag, yet carries multicast when a socket names it by index. `IP_MULTICAST_LOOP` and TTL default to 1. `IP_MULTICAST_ALL` defaults to 1, which delivers every group that any socket on the host joined to every socket bound to the same port, so a receiver of the incremental group would also get another group's packets.
**Rejected:** letting the routing table pick the interface (the route differs between a laptop, the container and CI); binding to INADDR_ANY (with ALL at its default it hears other groups on the same port); a blocking send (one slow kernel buffer would stop the feed for every receiver, while UDP loss is already handled by the sequence numbers and snapshots); one socket per receiver for both groups (the two streams would share one buffer, and a burst of snapshots could push out incremental packets).
**Consequence:** a packet the sender drops is a gap for every receiver, which the snapshot stream repairs, and the sender's dropped count says it happened. Tests and tools bind port 0 so runs side by side never share a port.
**Checked by:** socket tests on `lo` (options set as asked, ALL turned off, bound to the group, packets whole and in order, two groups on one port stay apart, two receivers both get every packet, truncated and too-big packets counted); a receiver test where the kernel really drops packets and the handler recovers; the mutation check of 8b-1, which caught ALL left on, binding to any address, reading without MSG_TRUNC and ENOBUFS counted as a failure.

## D-057 (2026-11-22): The publisher thread flushes when its queue runs empty, and the pipeline takes the publisher as a template
**Choice:** `pipeline::FeedWorker` (`include/litbook/pipeline/feed_worker.hpp`) pops market events and hands them to `FeedPublisher`. It sends the open packet as soon as the event queue runs empty, so all the events of one order usually leave in one packet and no event waits for a timer. After at most 64 events it checks the clock and sends a due snapshot or heartbeat, so a queue that never runs empty cannot starve the snapshot stream. In blocking mode it sleeps on its doorbell, but only until the next snapshot or heartbeat is due (rounded up to whole milliseconds, at most one second). `BasicThreadedGateway<Book, Queue, PublisherTemplate>` builds `PublisherTemplate<Queue<MarketEvent>>`, and `ThreadedGateway<Book, Queue>` stays the Phase 7 pipeline with `PublisherStub`. Each stock is listed with the publisher right after the engine, and `FeedWorker::add_symbol` checks that the feed's locate equals the engine's `SymbolId`.
**Rejected:** a flush timer (adds up to its period to every event); one packet per event (an order that trades through three levels would cost three system calls and three packets); sleeping with no timeout (the snapshot stream would stop whenever the market is quiet); a publisher parameter that is a finished type. With that design callers would write `Queue<MarketEvent>` inside a partial specialization whose `Queue` is a concept-constrained template template parameter, and Clang 21.1 crashes on exactly that (a 12-line reproduction was kept). GCC compiles it. The `requires` clauses of both publishers became `static_assert`s so the class templates match `template <concurrency::MessageQueue> class`.
**Consequence:** a blocking worker cannot keep a snapshot spacing below one millisecond unless events wake it often enough, because `poll()` sleeps in whole milliseconds. The default spacing is 1 ms, so this costs nothing by default, and `litbook_feed_recovery --spin` shows the shorter spacings.
**Checked by:** FeedWorker tests driven by hand (directory at start, events wait for the queue to run empty, snapshots and heartbeats only when due, Stop ends the session, the sleep timeout rounding and limit, locates checked) and on threads (a sleeping worker woken only by its deadline, spinning and sleeping workers publishing every event); the whole exchange with the feed on four setups (SpscQueue and MutexQueue, spin and block), including a listener that joins late.

## D-058 (2026-11-22): A receiver that hears nothing for three heartbeat intervals says it is silent, and does not pretend the session ended
**Options:** (1) Keep waiting for End of Session. (2) Treat a long silence as End of Session. (3) Report silence as its own state.
**Choice:** (3). `FeedReceiver` notes when the last packet of its session arrived on either stream, by a clock passed in its configuration (CLOCK_MONOTONIC by default). Once it has heard the feed, `silence_limit` (default 3 s, three heartbeat intervals) with no packet makes `silent()` true and counts a silence. The books are left as they are, because a silence by itself says nothing about lost messages. The next packet clears it, and if messages were lost in between, the handler finds the gap from the sequence numbers and recovers as usual. `litbook_feed_listener` exits with 3 and a `silent:` summary, where End of Session gives 0 and `ended:`.
**Why:** a running publisher sends a heartbeat at least every second on the incremental stream and a snapshot every millisecond on the other, so several seconds of nothing on both means the publisher or the network is gone. 8b-1 showed that a receiver that falls behind in the last burst can lose End of Session with nothing to reveal it, and the listener then waited forever.
**Rejected:** (1) hangs forever after a lost End of Session. (2) reports a network fault as a normal close, so a consumer could take stale books for the final ones. Marking every stock stale on silence was also rejected: if the next packet carries the expected sequence number, nothing was lost and the books were right all along. Silence before the first packet does not count, so a listener started before the exchange waits for it.
**Checked by:** receiver tests on a fake clock (no feed is never silence, the limit exactly and one nanosecond before it, a heartbeat clears it and a second silence is counted again, lost packets during a silence are recovered after it, limit 0 turns it off, packets of another session do not count, a missing clock throws), and a listener test that kills the gateway with SIGKILL and expects exit code 3.

## D-059 (2026-11-22): A journal of the inbound requests, in little-endian records with a CRC32C each, read through a memory map
**Choice:** the journal (`include/litbook/journal/`, `docs/JOURNAL.md`) holds every request the matching thread handles, exactly as `pipeline::Request` carries it (owner, gateway timestamp and the raw OUCH bytes), plus setup records for the order entry configuration, every stock with its full book configuration and its SymbolId, and every account's risk limits. So a journal is enough to rebuild the exchange without its command line, and it never holds a password. Each record has a 24-byte header (length, type letter, owner, sequence number, timestamp), the payload and a CRC32C of the rest. Numbers are little-endian and written field by field. The decoder checks the checksum right after the length and then every other field, so decoding is canonical. CRC32C has a table version and a hardware version (`__crc32cd` on arm64, `_mm_crc32_u64` on x86), each compiled with a target attribute on one function and chosen at runtime from the CPU's feature bits. A reader maps the whole file with `mmap` and walks it. Where the good records stop, it searches every later byte offset for a good record, and calls the end corrupt if it finds one (recovery refuses) and torn if it does not (recovery cuts it off).
**Rejected:** big-endian like the wire protocols (nothing outside litbook reads the file, and every machine it runs on is little-endian); copying `Request` into the file with `memcpy` (its padding bytes are undefined, so they would change the checksum from one build to the next); journaling decoded messages (the bytes the client sent are the ground truth, and the decoder itself may change); a checksum per batch instead of per record (one bad byte would throw away a whole batch, and a torn batch could not be cut at a record boundary); zlib's CRC32 or a fast hash such as xxHash (only CRC32C has an instruction on both arm64 and x86, and a hash would be a new dependency); building the whole project with `-march=armv8-a+crc` (the compiler could then use the instruction anywhere, and the program would crash on a CPU without it); reading the file into a vector (twice the memory for a day's journal) or in chunks (a record can straddle two chunks); treating every bad byte as the end of the journal, as many logs do (damage in the middle would silently drop every record after it).
**Measured first:** RFC 3720's five test vectors, the bitwise algorithm, the table and the hardware instruction agree (32 zero bytes give 0x8A9136AA). The container's CPU has the CRC extension, but neither GCC nor Clang turns it on by default (`__ARM_FEATURE_CRC32` is not defined without `+crc`), and a `target("+crc")` attribute on one function compiles with both. A Python version of the format, written separately for the fuzz seeds, produced journals that the C++ reader accepts as clean.
**Found by the fuzzer:** a Frame's payload is chosen by the client, so it can hold the bytes of a whole valid record. If a crash cuts that Frame short, the search finds the hidden record and the journal looks corrupt. The direction of the mistake is safe (recovery stops, nothing good is cut), so the rule stays, documented with a unit test and a regression input.
**Checked by:** golden bytes for the header and every record type; round trips at the extremes of every field; every cut of a record is Incomplete, every changed byte after the length a bad checksum, and every field rule has its own test; torn tails at every byte of the last record, zeros after the end, damage to five different records, sequence breaks and duplicates; replay of random 6,000-request streams on all three books giving the same replies, market events, end state and future as the live run, a journal written over MapOrderBook replayed into the other two, replay equal to what `MatchingWorker` sent when driven by hand, a torn tail left out, every replay refusal, and no allocation while replaying after setup; `journal_fuzzer` with seeds and a regression input, and `JournalFuzzCorpusReplay` in every build.

## D-060 (2026-11-22): The journal writer appends into memory, commits a batch with one write, and stops for good after any failed write or sync
**Choice:** `journal::JournalWriter` encodes each record into a buffer allocated at startup, with the next sequence number. Appending never makes a system call. `commit()` writes everything since the last commit, continuing partial writes and writes interrupted by a signal, which is group commit. The policy says how far a commit goes. Buffered writes only once half the buffer is used (benchmarks only, a process crash loses the rest), Write calls `write()` (survives a process crash, the default), and Sync adds `fdatasync()` (survives a power loss on real hardware). Any other write error, a write that takes nothing, or a failed sync stops the writer, and every later call returns Stopped. A new journal is created with `O_EXCL` and, under Sync, its directory is synced too. `resume()` checks that the file still has the length the scan saw, cuts a torn tail with `ftruncate`, and opens the file with `O_APPEND`. The system calls are function pointers in the configuration, so tests swap in writes that take three bytes at a time, get interrupted, run out of space or fail to sync.
**Rejected:** writing inside `append` when the buffer fills (a system call would hide in what looks like a memory operation, and the caller could not say which call does I/O); retrying a failed `fdatasync` (Linux may have dropped the unwritten pages and cleared the error, so a retry can report success for lost data, which is why PostgreSQL stops on such an error since 2018); `O_DIRECT` or `O_DSYNC` for now (they need aligned, padded writes, and their behavior in the Docker VM is unverified, so they wait for a bare-metal machine); reusing the gateway's `Fd` (its header pulls in the whole session layer).
**Consequence:** a crash during a commit can leave at most a torn last record, which `scan_journal` finds and `resume()` cuts. The Write policy is what a `kill -9` crash test can prove. On the development machine the Sync policy cannot be proven to survive a power loss, because the disk is virtual and `/work` is shared from macOS, where plain `fsync` does not flush the drive cache. Tests and measurements put journals on `/tmp`, the virtual machine's own disk.
**Checked by:** writer tests for the header, consecutive numbers, one write per commit, a full buffer, refused records, each policy's system calls, partial and interrupted writes giving the same file, a disk that fills mid-record (the file is a good prefix plus a torn record), a failed sync staying failed when the next one would work, the destructor flushing, moves, and resume after a torn tail and a clean end; a no-allocation test over 50,000 appends and their commits.

## D-061 (2026-11-22): A journal thread between the gateway and the matching thread, one commit per batch, and a stop on the first failure
**Choice:** `pipeline::JournalWorker` (`include/litbook/pipeline/journal_worker.hpp`) runs on a fourth thread of the pipeline. The gateway pushes requests into its queue as before, and the journal thread takes every request that waits (at most 64, and never more than fit in the writer's buffer), appends them all, writes them with one `commit()` (one `write()`, plus one `fdatasync()` under the Sync policy), and only then pushes them on to a second queue that the matching thread reads. So no reply and no market data can leave the exchange before the request that caused it is in the journal. Stop is journaled and flushed like a request and then passed on. If an append, write or sync fails, the batch is never passed on, the worker tells the pipeline once (which stops the gateway, so the session ends normally), and from then on it throws requests away until Stop, which it still passes on so the matching thread answers Stopped. `stop()` rethrows the failure as a `std::runtime_error` with the errno text. The journal is optional. Without one there is no fourth thread and the matching thread reads the gateway's queue exactly as in Phase 8. The request doorbell wakes whoever reads the gateway's queue, and a second doorbell wakes the matching thread, so each doorbell still has one consumer (D-053). **This supersedes the line of D-052 that said the publisher thread becomes the journal writer in Phase 9.** The journal must hold the inbound requests in the order the matching thread handles them, and the publisher thread only sees what matching produced.
**Rejected:** journaling on the matching thread before each request (every disk write would stall the books, and one write per request gives up group commit); on the gateway thread (a slow disk would stop it from reading every socket, and Busy would have two causes); in parallel with matching while holding back the replies until the journal catches up (the market data feed would publish trades whose requests are not on disk yet, and every reply would need a second queue to wait in); a fourth thread that always runs, even without a journal (an extra thread hop of about 15 us in this VM for nothing).
**Measured first:** in Linux 6.10 `generic_perform_write` stops between pages when a fatal signal is pending and returns the bytes it already copied, so a SIGKILL during a large commit can leave a torn last record. That is why recovery must cut a torn tail and the crash test accepts one.
**Consequence:** a request whose batch failed may still be on disk in full. Recovery then replays it, although its client never got a reply, which is the usual write-ahead rule (once a request is in the journal it has happened). Its replies use up sequence numbers like the cancels of cancel on disconnect.
**Checked by:** JournalWorker tests driven by hand (one write per batch with the output queue empty at the time of the write, batch limits, Sync syncs once per batch, Stop flushed even under Buffered, a failed write or sync forwards nothing and tells the listener once, later requests thrown away and Stop passed on, a full output queue waited for, a sleeping worker woken by its doorbell); the threaded pipeline with a journal on four setups, whose journal replays to exactly the bytes the clients got; a failed write that ends the session by itself and makes `stop()` throw; no allocation while the pipeline with a journal serves 20,000 frames.

## D-062 (2026-11-22): Recovery rebuilds the exchange from the journal at start, refuses what it cannot trust, and starts a new feed session
**Choice:** `BasicThreadedGateway::start()` opens the journal before any thread runs. A missing file is created with the setup records. An existing one is mapped and scanned. A bad header or corruption in the middle refuses the start with a message, because cutting there would lose good records. The setup records at its start must equal the ones this start would write (from the command line), compared by type, owner and payload, and the first difference is named in the message. Then every record is replayed into the matching thread's own order entry layer, with its replies and market events going to a recovery sink instead of the queues. The sink counts the replies per account and gives the level updates to the publisher's level copy without sending them. The file is unmapped, the writer resumes (cutting a torn tail), and a new record type, Restart (`A`, no owner, no payload), is written, followed by one Cancel All for every account with cancel on disconnect, whose connections the crash took away. Those records are flushed before they are applied, the same order the journal thread uses, so the next replay gives the same result. Each account's next sequence number becomes 1 plus its replies (`restore_next_sequence`), and the market data feed starts a new MoldUDP64 session named after the Restart record's sequence number, so receivers fill their books again from snapshots. A journal that holds only the file header is treated as new, and one that ends inside its setup records gets the missing ones and counts as a restart. `litbook_gateway --journal PATH [--sync write|sync]` runs the pipeline in blocking mode (with `PublisherStub`, or `FeedWorker` with `--feed`) and waits on a `signalfd` and the pipeline's "finished" eventfd, so a journal failure ends the program with exit code 1.
**Rejected:** taking the setup from the journal and ignoring the command line (accounts are numbered by the order of the `--account` flags and passwords are not journaled, so a changed command line would silently give one account's orders to another); leaving the orders of cancel on disconnect accounts resting (their owners asked for them to go away when the connection does); continuing the old feed sequence numbers (the incremental sequence is not journaled); a feed session named by the clock (not deterministic, and two restarts in one second would share a name); building a second order entry layer for the replay and moving it into the matching thread (it holds references to its sinks and cannot move, so a sink setter was added instead, which keeps the matching hot path unchanged); journaling inside the single-threaded gateway as well (a second write path and a second recovery path to test, and `write()` on the thread that serves every socket); `sigwait` in the tool (it cannot also wait for the exchange to end by itself).
**Consequence:** messages a client never received before a crash cannot be sent again yet, because a login that asks for an old sequence number is still refused. Replaying them from the journal is a Later item. A crash between creating the journal and writing its 32-byte header leaves a file that is refused, and an operator removes it.
**Checked by:** recovery tests on four setups (a restart rebuilds the book so an order from before trades after it, sequence numbers carry on, a third start sees both earlier runs, a cancel on restart is journaled and replays the same, a torn tail is cut and the good records kept, a corrupt journal and a file that is not a journal are refused and left alone, another setup is refused and named, a journal that ends inside its setup is completed, an empty journal is new); the feed after a restart (new session name, rebuilt levels in the copy); session layer, publisher and order entry tests for each new call; `litbook_gateway` smoke tests (restart keeps the book and the sequence numbers, a bad or foreign journal exits with 1, bad journal arguments exit with 2, `--sync sync` syncs); and a crash test that kills the program with SIGKILL 20 times at random points, a quarter of them right after it was spawned, and checks after every kill that every message any client saw is in the replay of the journal with the same sequence number and bytes, that the journal is never corrupt, that every login gets 1 plus the replies the journal gives the account, and that a last clean run ends with the replay's live orders.

## D-063 (2026-11-22): A snapshot is the visible state of the exchange as of one journal record, in litbook's own little-endian format with one CRC32C
**Choice:** `journal::Snapshot` (`include/litbook/journal/snapshot_format.hpp`, layout in `docs/JOURNAL.md`, "Snapshots") holds the setup records, each account's reply count and last UserRefNum, the order entry layer's counters, every book's match counter, every live order in the order of its account's list, and every resting order book by book (bids then asks, best first, time priority within a price), tagged with the sequence number and time of the last record it includes. ## D-064 (2026-11-22): Books and the order entry layer get restore calls that send no events, and a restored state must capture back to itself
**Choice:** the `OrderBook` concept gains `for_each_resting(side, visit)` (best first, in priority order), `restore_resting(order)`, `next_match_id()` and `restore_next_match_id(m)`. `restore_resting` checks the price (tick and band), the quantity (a whole lot), a duplicate id, an order that would cross the other side and a full book, in that order, and returns a `RestoreStatus`. ## D-065 (2026-11-22): The journal is a directory of segment files named by their first sequence number, and the journal thread rotates them without allocating
**Choice:** `--journal` now names a directory (`include/litbook/journal/journal_directory.hpp`). Segments are named by their first record's sequence number in 20 digits, and snapshots by their last. The journal thread starts a new segment after a set number of records (`records_per_segment`, one million by default, `--segment-records`), checking after each forwarded batch. `JournalWriter::rotate(path, directory)` flushes, creates the next file with `O_EXCL`, closes the old one and writes the new header, and under Sync syncs the header and the directory. It keeps its buffer and builds the name in a fixed `PathBuffer`, so rotating never allocates. Rotating a segment that holds no record does nothing. `scan_segment_chain` maps and scans every segment and checks that they form one chain: the first may start anywhere, each later one must start where the one before it ended, a name must match its header, and only the last may end torn. A last file that holds only the start of the header the chain expects next is a torn rotation, which recovery deletes. **This revises the consequence of D-062** that a crash between creating the journal and writing its header leaves a file that is refused. Inside a directory that cut file is recognized and removed, for the first segment as for any later one.
**Rejected:** one file that is rewritten or truncated at the front after a snapshot (the file would no longer be append-only, and a crash during the rewrite could lose good records; deleting a whole segment is one `unlink`); naming segments by a counter (the name could not tell which records a file must hold, so a missing or renamed file would go unnoticed); rotating on a timer (the snapshot thread's work would no longer be bounded by a number of records); keeping `--journal FILE` beside the directory form (two recovery paths to test for one feature).
**Found by the tests:** the first `rotate()` had no rule for an empty segment. A segment that holds no record has the same first sequence number as its successor would, so `O_EXCL` refused the new name and the writer stopped. Hence the no-op rule and its test.
**Measured first:** man7.org `rename(2)` (the new name is replaced in one step, with no moment where it is missing) and `fsync(2)` (a file's directory entry needs a sync of the directory). A probe (`build/p9/unlink_mmap.cpp`) showed that after `close` and `unlink` all 8,192 bytes of a mapped file still read back, so the snapshot thread may keep a removed segment mapped.
**Checked by:** writer tests for rotation (the new segment starts with the next sequence number, records buffered under Buffered still go to the old segment, an existing file is never overwritten and the writer stops, Sync syncs the old file, the new file and the directory, a directory that cannot be synced stops the writer, an empty segment is not rotated); directory and chain tests (21: names, listing and sorting, a late first segment, gaps, name mismatches, torn inside, torn last, a cut header that is and is not the expected one); JournalWorker segment tests; recovery tests for a torn rotation, a missing middle segment and old segments removed; and the crash test with 16-record segments.

## D-066 (2026-11-22): A snapshot thread replays closed segments into its own copy of the exchange, snapshots are written at start and at a clean stop, and the newest two are kept
**Choice:** with snapshots on (`keep_snapshots`, 2 by default, `--keep-snapshots`), the exchange writes a snapshot at every start, after recovery and before any thread runs, and another at a clean stop after every thread has finished. With segments and `--snapshot-thread on` (the default) a fifth thread, `pipeline::SnapshotWorker` (`include/litbook/pipeline/snapshot_worker.hpp`), keeps a second copy of the exchange (the shadow), built from the start snapshot. The journal thread only stores the closed segment's end in an atomic and rings the snapshot thread's own doorbell. The snapshot thread then maps each closed segment, replays it into the shadow, captures the state into a reserved `Snapshot`, encodes it into a buffer sized at startup for the largest possible snapshot, and writes it through a temporary file that is synced (under Sync) and renamed (`journal/snapshot_store.hpp`). Recovery starts from the newest snapshot that decodes, has this start's setup and is continued by the segments, and falls back to older ones. After each snapshot, older usable snapshots beyond the newest `keep` are removed, then every segment whose records are all in the oldest snapshot kept. A snapshot that cannot be used is never removed. If the snapshot thread fails, it stops taking snapshots and the exchange runs on. The tools print what happened, and `litbook_journal` reads a directory (`verify`, `dump`, `replay [--from-start]`) and writes a snapshot offline (`snapshot DIR`) through the same code (`journal/directory_replay.hpp`).
**Rejected:** snapshotting on the matching thread (it would stop matching for the whole encode and write, which grows with the book); a `fork()` with copy-on-write, as Redis does (fork in a process with five threads copies only the calling thread, and the child would inherit locks and queues in whatever state they were in); stopping every thread for a moment to copy the state (the same pause, smaller); a snapshot only at a clean stop (a crash would then still replay from the last clean stop, which may be a whole day); removing damaged snapshots (an operator should see what went wrong); failing the exchange when the snapshot thread fails (a snapshot only shortens recovery, and the journal is still complete).
**Consequence:** the snapshot thread uses as much memory again as the books. Encoding, writing and replaying allocate nothing after startup, but retention lists the directory, which allocates once per snapshot on that background thread. So the pipeline's no-allocation test runs with segments every 1,000 records and snapshots off, which covers rotation on the journal thread, and the snapshot thread is checked by its own tests and the crash test. A snapshot as of a record of a segment that is still open is only taken at start and at stop, so after a crash recovery replays at most one segment plus whatever the snapshot thread had not reached.
**Checked by:** snapshot store tests (write and read back, replace, a failed rename leaving no temporary file, a missing directory, a damaged file and a name that disagrees with its contents refused, retention with keep 0, keep 1 and more kept than exist, nothing removed without a good snapshot, the last segment always kept, the continued rule at both ends); snapshot worker tests (nothing happens until a segment closes, each closed segment gives a snapshot equal to the true state, several closed segments caught up in order, older snapshots and covered segments removed, a damaged or missing segment stopping only the snapshots, a start snapshot that does not fit refused, and on its own thread it sleeps until a segment closes and stops when asked); recovery tests on four setups (a clean stop writes a snapshot and the restart starts from it, a damaged newest snapshot falls back to the one before, segments and the thread let old files go, later records after the stop snapshot are used, a snapshot and a full replay give the same exchange); `DirectoryReplayTest`; `litbook_gateway` smoke tests for every new flag and refusal; `litbook_journal` directory smoke tests; and the crash test with 16-record segments (26 kills; every snapshot whole, continued and replaying forward to exactly the full replay's state; recoveries from snapshots; old files removed under kills in the last rounds).

## D-067 (2026-11-23): The client key puts the account in the lowest digits, so accounts' recent orders do not pile up in one probe run
**Choice:** `OrderEntry` finds a live order by its account and UserRefNum through `protocol::client_map_key(owner, user_ref, max_owners)`, which is `user_ref * (max_owners + 1) + owner` in 64 bits. Every pair gets its own key and the largest is exactly 2^64 - 1, so nothing overflows. The account is the lowest digit in base `max_owners + 1`, so the keys of all accounts are interleaved into one increasing range, the same pattern as exchange order references, and the fold gives every key of such a range its own home slot (within each block of table-size keys it XORs every key with the same value) while keeping recent orders in nearby slots.
**Why:** the key was `owner << 32 | user_ref`. `FlatIdMap` folds the key into the table index (D-039), which shifts the owner down to `owner << 11` in a table of 2^21 slots, the size the default `max_live_orders` builds. Each account's newest UserRefNums are its densest live orders, so the four accounts' recent orders landed on almost the same slots and merged into one run. Linear probing then walked that run on every insert, lookup and erase. Found by the first benchmarks with a large live state (`BM_OrderEntrySteady`, `BM_SnapshotRestore`): at 102,999 live orders a frame took 30.4 us instead of 0.18 us after the fix, and restoring a snapshot took 764 ms instead of 18.3 ms (BENCHMARKS.md, 2026-11-23). Every earlier benchmark held about 2,000 live orders or fewer, and the ITCH replays do not use `OrderEntry`, which is why it was not seen before. The order reference map (`by_ref_`) was never affected, because exchange order references come from one increasing sequence.
**Learned from the mutation check:** density was never the problem. A mutant without the `+ 1` (`user_ref * max_owners + owner`, still unique because owner 0 is never used) was just as fast and survived as an equivalent mutant. What hurt was that every account had a separate key range and the fold laid those ranges on top of each other. The `+ 1` stays because it makes the owner a plain digit, which makes uniqueness obvious.
**Rejected:** a scattering hash for this map (Fibonacci or a mixing finalizer), which also bounds probe runs but gives up the cache locality D-039 measured and would need a hash parameter on `FlatIdMap`; a separate map per account (an allocation per account at startup and a second lookup per message); swapping the halves to `user_ref << 32 | owner` (the fold then mixes the UserRefNum's high bits into the owner's and the runs are harder to reason about).
**Consequence:** no file format changes, since neither the journal nor the snapshot stores these keys, and `FlatIdMap` is never iterated, so replay stays deterministic. The key now depends on `max_owners`, which is fixed for the life of an `OrderEntry`.
**Checked by:** a regression test written first (`ClientMapKeyTest.DenseRecentOrdersOfSeveralAccountsDoNotPileUp`, every UserRefNum 1 to 60,000 of four accounts live in a map of the default size; longest probe 188,191 before the fix, at most `max_owners` after), uniqueness at the largest values, no overflow at the largest `max_owners`, accounts far apart in UserRefNum, and the whole test suite.

## D-068 (2026-11-23): The load generator is an open loop client in its own process, timed from each request's due time, with its sessions shared over a few epoll threads
**Choice:** `litbook_loadgen` (`tools/loadgen_main.cpp`, library in `include/litbook/loadgen/`) connects to a running `litbook_gateway` like any client. Every account gets one SoupBinTCP session (litbook allows one connection per account), and the sessions are shared out over a few client threads, each driving its sessions through one epoll instance without sleeping. The whole run is one schedule of `rate` requests per second, and request i is due at floor(i * 1e9 / rate) ns after the start, in integer math that never drifts (`pacer.hpp`). Session s of n sends requests s, s + n, s + 2n and so on, which spreads the sessions evenly. A due request is sent whether or not earlier ones were answered, unless its session already has `max_in_flight` requests waiting. Each request kind (enter, cancel, replace) gets two histograms per pass. Response time runs from the due time to the moment the first reply has been read, and service time from the real send. Send lag (how late requests left) is reported too, and so are the requests that were due but never sent. Each printed percentile is the median over the passes (D-034). Each session trades one stock around a fixed middle price with a seeded mix of passive orders, aggressive IOC orders, cancels and replaces, and learns what happened only from the replies (`OrderFlow`). `litbook_gateway --load-accounts N` makes the accounts L00001 to L0000N with cancel on disconnect, so a run leaves the book empty, and the gateway takes 16 more connections than it has accounts.
**Rejected:** a closed loop client that sends, waits for the reply and only then sends again (when the exchange stalls the client stops sending, so the stall is measured once instead of for every request it delayed, which is coordinated omission; and its rate is set by the latency instead of by the test); a thread per session (200 sessions on 11 virtual CPUs would measure the scheduler); running the exchange inside the tool as `litbook_gateway_latency` does (a load test should cross the same process boundary as a real client and run unchanged against the inline gateway, the pipeline with the feed and the pipeline with the journal); `SteadyStream` from the journal benchmarks (it lives in `tests/`, guesses which orders are live without reading replies, and one request in five names an order that already filled); `std::chrono` intervals added up per request (rounding drifts); a Poisson schedule (bursts are realistic, but the even schedule makes the first numbers easy to reason about, and a Poisson option is a Later item).
**Consequence:** the client shares the machine with the exchange, so its own cost is part of every number, and send lag says when it fell behind. A run that is far past what the exchange can take spends its time on requests that were due during the warm up, which are never timed, so its tables can be empty while the unsent count is large. UserRefNums must keep rising for the whole day per account, so a second run against the same gateway needs `--first-ref` above the number the previous run printed.
**Checked by:** pacer tests against a 128-bit formula (every step at each due time, up to about 31 years at rates from 1 to 1e9 per second, no drift over a day); an end-to-end test against an in-process gateway (8 sessions on 2 threads: every request answered or ignored, scheduled = sent + unsent, both sides of every trade seen, net position 0, service time never above response time, no live orders after the run); a wrong password failing only its own session; reused UserRefNums reported; an overload that shows up as unsent requests and lag rather than lost ones; refused configs and a missing server; `litbook_gateway --load-accounts` and `litbook_loadgen` smoke tests (a healthy run, a rate sweep carrying the UserRefNums, a second run refused and then fixed with `--first-ref`, a wrong account, bad arguments).

## D-069 (2026-11-23): A request without a reply counts as handled once a later request of its session is answered, and every session ends with a fence
**Choice:** each session keeps its requests that wait for a first reply in send order (`InFlightQueue`, a ring sized at startup). An Enter is answered by Order Accepted or Rejected, a Replace by Order Replaced or Rejected for its new UserRefNum, and a Cancel by Order Canceled with reason U. Executions, IOC remainders and the cancel that follows a failed replace answer nothing. The exchange handles one account's requests in the order they arrive and sends their replies in that order, so when a reply answers a request, every older request still waiting was handled without a reply and is counted as ignored. This happens to a Cancel or Replace that names an order which filled while the request was on its way, which the exchange drops silently, as OUCH does. `OrderFlow` marks an order busy while a Cancel or Replace for it waits and never names it twice, so every reply matches at most one waiting request. After the schedule each session sends a fence, an Enter for a stock that is not listed, which is always rejected. Its reply proves that everything before it was handled, so the run can end without waiting on a timeout.
**Rejected:** a timeout per request (it would mix slow replies with ignored requests, and the run would end only after the longest timeout); a hash map from UserRefNum to send time (a Cancel and an Enter can carry the same UserRefNum, the map would never learn which requests were ignored, and it allocates); never cancelling or replacing an order that might fill (it would leave out exactly the race a real client lives with); an Enter that rests as the fence (it would change the book and the fill counts).
**Learned:** the first version of the test that drives two flows against the real `OrderEntry` with random delays failed. The flows were right, and the test delivered one client's last replies before the other client's last orders had traded with them. Delivering only after every request was handled fixed it.
**Fixed in 10a-2 (two fences and a wait between them):** the first load runs with four client threads sometimes printed a net position that was not 0. Each thread logged its sessions out as soon as its own fences were answered, while a session on another thread could still trade with their resting orders, and the replies about those trades went to a session that had already left. Now every thread, after its first drain, keeps reading until every thread has finished its first drain. At that point the exchange has handled every request of the run, so no more trades can happen. Each session then sends a second fence, whose reply proves that every reply sent to it before (including those late trades) has been read, and only then logs out. A regression test (`LoadRunTest.EveryTradeIsSeenFromBothSidesWithManyThreads`) serves a slowed gateway that reads only about two orders per session per poll, so sessions end with backlogs of different lengths. It failed in 4 of 5 invocations before the fix and in none of 10 after it.
**Checked by:** queue tests (ignored requests counted by kind, a reply that only follows changes nothing, kinds must match as well as the number, wraparound); `OrderFlow` tests (busy orders never named twice, a failed replace ending with the cancel of the original, a replace moving the order to its new number); two flows trading through the real order entry layer with random delays in both directions, where cancels of filled orders really happen and every request ends answered or ignored, no Enter is ever ignored, and each flow agrees with the exchange about its live orders; and the end-to-end tests, where sent equals answered plus ignored for every kind in every session.

## D-070 (2026-11-23): FlatIdMap keeps its entries in Robin Hood order, so an erase stops at the first entry that is already home
**Choice:** every slot of `FlatIdMap` stores how far its key sits from the key's home slot, in what used to be padding (a slot is still 16 bytes). An insert that reaches an entry closer to its home than the new key already is puts the new key there and carries the old entry on (Robin Hood hashing). That keeps a rule along every run of slots: the next entry is at most one step further from home than this one. A lookup stops as soon as it meets an entry closer to home than the key it wants, and the backward-shift erase moves back only the entries right after the hole that are not home, stopping at the first empty slot or the first entry already in its home slot. The fold hash (D-039) is unchanged. `erase_walk()` counts the entries erases have moved back, for tests.
**Why:** a load test whose client kept up to 256 requests in flight per session (more than the gateway's 64 per account) got only 0.78 to 0.87 million requests per second through the threaded gateways with the feed or the journal, against more than 7 million for the inline gateway, while the matching thread sat at 100% (BENCHMARKS.md, 2026-11-23, window rows). A profile put about 59% of the matching thread's samples in `OrderEntry::release` and `SortedOrderBook::remove`, which both erase from `FlatIdMap`. The fold gives a range of recent order IDs one long run of slots that each hold their own key, so lookups cost one slot. The old erase, however, read every slot to the end of the run after the hole, because in plain linear probing any later key might have to move back. An instrumented copy of the gateway counted 261 slots per erase on average (largest 1,011) in that run, against 0.7 with 64 in flight. So D-067's conclusion that density never hurt holds for inserts and lookups, but not for erase.
**Measured after:** the same runs reached 8.24 to 8.28 million requests per second with the feed, 5.03 to 5.16 with the journal, and 8.25 to 8.62 inline (three rounds each).
**Cost:** single operations on `FastOrderBook` got slower in Google Benchmark, about 3 ns each (a rest and cancel pair 44.2 to 50.3 ns, a rest and match pair 52.0 to 56.2 ns, slower in all three alternated pairs). Whole order streams, replays and snapshot restores moved by a few percent either way. The likely cause is that an insert now walks twice, once to check for a duplicate and once to place the key. Merging the two walks is a Later item. The trade was taken because a worst case 10 times slower under a realistic load is worse than a few nanoseconds on the best case.
**Rejected:** going back to a scattering hash such as Fibonacci (it also breaks up the runs, but it reverses D-039 and gives up the locality that won on the ITCH day); tombstones, which mark erased slots instead of shifting (erase becomes O(1), but lookups must walk over the markers and the table needs a periodic rebuild, which is a pause on the hot path); a cap on the run length checked at erase (it only hides the cost).
**Checked by:** a regression test written first (1,000 sequential keys, erasing from the oldest: 12,252 slots walked before the change, and the test allows at most one move per erase), the existing churn test against `std::unordered_map` and the tiny-table collision and wraparound test, both now also checking every stored distance and the Robin Hood rule, the strided and sequential pile-up tests, and every book, order entry, journal and snapshot test that uses the map.

## D-071 (2026-11-23): Python clients through pybind11, with the logic in C++ classes, a blocking order client that knows when a request cannot be answered, and a feed book with its own reader thread
**Choice:** pybind11 v3.1.0 (released 2026-08-06, fetched by FetchContent and pinned by the SHA-256 of the tag tarball, built with Python from `python3-dev`) builds one module, `litbook` (`python/litbook_module.cpp`). The module only converts values. The logic is in three library classes in `include/litbook/client/`. `OrderTracker` keeps an account's open orders from the replies alone and says which reply answers a request. `OrderClient` is a blocking client made of a socket, the load generator's `ClientSession` and an `OrderTracker`. Its `enter`, `replace` and `cancel` each send one request and wait for its answer, and every other reply goes to an event queue in arrival order. It picks rising UserRefNums by itself. `FeedBook` runs a `FeedReceiver` on its own thread and gives out copies of the best prices and the depth under a mutex, with a version number to wait on. Prices and quantities stay integers in Python, and a float or a value that does not fit is refused with a TypeError. Every call that can wait releases the Python interpreter lock while it waits. The module is built in the presets without sanitizers (debug, release, their Clang versions and profile) through `LITBOOK_BUILD_PYTHON`, and links `litbook_pic`, a second copy of the library compiled as position independent code. Its Python tests (`python/tests/`, unittest) start the real `litbook_gateway` and run from ctest, one ctest test per file.
**Why the cancel rule works:** a Cancel or Replace that names an order which filled on its way gets no reply (D-069). The exchange handles one account's requests in order and sends that account's replies in order, so the executions that filled the order were sent before the exchange even read the request. The client therefore stops waiting when the answer arrives or when the tracker says the order is no longer open, and both happen within one round trip. A timeout is only for a request the exchange ignores for another reason (a UserRefNum that is not higher than the account's last, for example on a second connection that starts from 1 again).
**Why the reader thread:** a feed receiver that is not read during a burst loses its tail, End of Session included (container gotcha found in Phase 8b). Python code that holds the interpreter lock, or a bot that sleeps, would leave the sockets unread. The thread waits on both sockets without the mutex and takes it only for the read, which never blocks.
**Why not under sanitizers:** checked in the container with a small instrumented library loaded into `python3` by ctypes (the same dlopen a module goes through). Without preloading, none of the four loads. GCC's ASan says its runtime must come first in the library list, GCC's TSan cannot get its static TLS block, and Clang's ASan and TSan miss their runtime symbols. With `LD_PRELOAD` of GCC's runtime both load, but TSan needs every thread's synchronization instrumented and the interpreter's lock is not, and LeakSanitizer would report the interpreter's own memory. So the sanitizer coverage comes from the GoogleTest tests of the three classes, which run in all 8 presets.
**Rejected:** writing the client logic in the binding file (it would only be tested from Python and never under a sanitizer); thin one to one wrappers of `ClientSession` and `FeedReceiver` (every bot would rewrite the socket loop); a fence order to end a cancel's wait, as the load generator does (it rests on the book and changes it); a timeout per cancel (it mixes slow answers with dropped requests and every cancel of a filled order would cost the whole timeout); a feed book that Python polls itself (lost tails, see above); turning on position independent code for `litbook` itself (simpler, but it changes the code generation behind every recorded benchmark and would need A/B runs to show it costs nothing); pytest (another dependency, and unittest is enough for these tests).
**Consequence:** only reads and writes inside a call move an order client's session, so a caller that pauses longer than the gateway's idle timeout (15 seconds) must call `events()` in between. The library compiles twice in the presets that build the module. `logout()` waits until the server closes the connection, so the account is free when it returns.
**Checked by:** `OrderTracker` and `answers`/`gone` unit tests (every reply type, replaces keeping executed shares, unknown orders ignored); `OrderClient` against an in-process gateway on its own thread (accepted and rejected orders, executions on both sides, IOC remainders, cancel and replace answered, cancel and replace of an order that filled before they arrived returning Gone well inside the timeout, a failed replace with its cancel as an event, an ignored Enter timing out, prices the wire cannot carry, wrong password, a second session of an account, no server, bad configs, a server that goes away, logout, and a scripted server that closes 200 ms after the Logout Request to show that `logout()` waits for the close); `FeedBook` over real multicast on loopback (unknown symbols, best and depth following level updates, waits, packets lost on the way (dropped by a switch in front of the socket) making both stocks stale while the last copy still answers, and snapshots making them live again, End of Session, silence, bad configs); 14 Python tests against the real gateway, two of which show that another Python thread counts at least a quarter as far during a blocking call as during a `time.sleep` of the same length. A mutation check on a copy of the tree caught 18 of 18 planted bugs after two test gaps were closed. The first version of the lock tests let the other thread run between reading the counter and making the call, so keeping the lock in `wait_update` went unnoticed, and no test checked that `logout()` waits for the close.

## D-072 (2026-11-24): Python bots keep their decisions in plain functions, quote around the other traders' prices, and run as threads in one simulated market
**Choice:** the bots are a package, `python/litbook_bots/`, with one module per job (`market_maker`, `noise_trader`, `book_view`, `simulate`, and small `prices`, `position` and `replies` helpers). Each module puts its decisions in plain functions that take values and return values (the quotes for a fair value and a position, how to move an order to a quote, the next random order, the picture of a book), and one loop class that waits on the network, calls them and sends what they say. The loop classes take the client and the feed book as arguments, so the tests hand them stand-ins (`python/tests/fakes.py`) and check them step by step. The bots tell replies apart by the name of their type (`replies.kind`), because the module's reply classes cannot be built from Python, and a stand-in with the same name then works.
The market maker estimates fair value as the middle of the best bid and offer that other traders show, which it gets from the feed's levels minus its own open orders. With one side empty it keeps its last estimate. Its center is the fair value moved against its position by a fixed number of price units per share (inventory skew), the bid is rounded down to a tick and the offer up, both stay a tick inside the others' best prices, and each side's size stops at the position limit, so a full fill can never take it past the limit. Quotes are post only, so the maker never takes liquidity. To move a quote it sends one OUCH Replace, and only when the price changes, the order shows more than the target or fills took it below half the target. It pulls its quotes while the feed says the stock is not live.
The noise trader draws everything from one seeded `random.Random`. It waits an exponential time between actions (a Poisson process, capped at one second so a stop is noticed), then takes liquidity with an IOC order a few ticks through the other side, rests a limit order 0 to 5 ticks behind the middle, or cancels one of its orders, with fixed weights and a cap on open orders. The waiting time is a float, but prices are worked out in integer ticks.
The book view renders lines of text in a plain function and draws them with curses, or prints them with `--once` and `--plain`. The simulated market starts `litbook_gateway` with its feed on loopback and accounts that cancel on disconnect, runs every bot as a thread with its own order client, shares one feed book between them, and stops them at a deadline. Then it checks the market from the outside: every match number was seen exactly twice with opposite sides and the same shares and price, positions add up to zero shares and zero cash, the feed printed one trade per match, the feed's book equals every bot's open orders added up per price, and the book is empty after the bots log out.
**Why the fair value leaves out the maker's own quotes:** the maker's quotes already include its skew. A maker that read the full book's middle as the market would see its own skewed quotes, skew again on the next requote, and walk the price away by itself while it holds a position.
**Why threads:** every wait in the module releases the interpreter lock (D-071), and the bots spend nearly all their time waiting. Each bot is still a separate TCP client with its own account, which is what the exchange sees. One process gives a clean stop at a deadline and lets the checks read every bot's fills and open orders directly.
**Rejected:** flat scripts (no shared code, and the logic could only be tested by running a whole market); the full book's middle as fair value (the feedback loop above); cancel and enter to requote (two round trips and a moment with no quote); a fixed interval between noise orders (every bot would act in step); numpy for the random numbers (a new dependency for what the standard library does); rich or textual for the view (dependencies) and hand-written ANSI escapes (curses already handles screen size and redraws); one process per bot (more realistic, but the results would need to be sent back to the launcher and stopping them is messier); adding constructors to the module's reply classes only for tests; pytest and Python linters (new dependencies).
**Consequence:** a run's decisions repeat for the same book states, but the book states depend on thread timing, so two runs with one seed are not the same run. A replay of a run would come from the gateway's journal. The feed can lag the maker's own replies by a moment, so a level that shows fewer shares than the maker's own orders there counts as the maker's alone, and an order of another trader at that price is missed until the feed catches up.
**Checked by:** unit tests of every decision function (including a 5,000-case property test that the bid stays below the offer and both stay on ticks and inside the others' prices, which found an off-tick clamp when the others' price is between ticks), loop tests with the stand-ins (fills, partial fills, the position limit, a stale feed, a replace that finds its order filled, a refused replace, a refused enter, fair value ignoring the maker's own quotes, the same seed giving the same orders, the noise trader's rate and stop), a maker against the real gateway that leans against a fill, `book_view --once` as a separate process against a real feed, and whole simulated markets that must pass every check. A mutation check on a copy of the tree caught 25 of 27 planted bugs. The two survivors both stopped the maker from forgetting the number of an order that had ended. They changed nothing, because the maker always asks the client whether an order is still open before it acts on it, so that code was removed instead of tested.

## D-073 (2026-11-24): A feed book that joined late is stale until it has read the incremental stream once
**Choice:** `FeedBook::status` and `best()` report a stock as live only when the feed handler says it is live and the handler has accepted at least one incremental packet (`stats().incremental_packets > 0`). Before that the stock is Stale.
**Why:** a receiver that joins after the session started can hear the snapshot stream first. The Symbol Directory there makes the stock known, and the handler counts a stock as live until it sees a gap, but it can only see the gap when an incremental packet shows a sequence number above the one it expects. Until the first heartbeat (up to a second in a quiet market) the book said Live while it was empty. FEED.md already said a late joiner should not trust its books before its first incremental packet, but `FeedBook` did not apply that rule. Found by `book_view --once` in a new process, which printed an empty book as live (an instrumented run showed Live, 0 levels and 0 incremental packets for about half a second, then the gap and the right book).
**Rejected:** a check in each Python bot (every caller would have to know the rule); changing the handler's own live flag (the handler is the protocol's state machine and its tests define live as "no gap seen", which is right for it; trust is a question for the reader of the books).
**Checked by:** `FeedBookTest.ALateJoinerIsNotLiveBeforeItHasReadTheIncrementalStream` (written first and failing: loses the start of the session through the switch sink, lets only snapshots through, expects Stale with 0 incremental packets, then a gap and live books with the level that never arrived on the incremental stream), and `BookViewProcessTest`.
